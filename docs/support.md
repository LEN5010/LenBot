# 支持组合与信任边界

面向部署者、插件作者和评估使用范围的维护者。本文是当前源码与配方的能力清单，不是已发布支持承诺。与同一提交的[安装手册](operations.md)、[插件兼容清单](plugin-compatibility.md)一起阅读；任务状态只在[产品路线](plan/README.md)，真实组合的验证记录归当前任务或发布观察材料。

## 支持如何判读

- **源码已适配／实验性**：有当前入口或配方，仍需实际组合的同版操作证据。
- **现场已验证**：必须指明源码与前端、操作系统／镜像、模型渠道与模型、平台实现及其所报版本（若有）、配置选择和原回执；只适用于该次已观察范围。
- **公开支持**：首个验收方向已选定，Linux/amd64 与 Linux/arm64 都纳入目标；OneBot 按所选消息／文件协议而非 SnowLuma 固定发行版本名单判读。模型职责、部署条件、现场回执与维护承诺仍需确定；不从方向选择、历史成功记录、构建通过或开关推导。
- **未提供的组合**：没有相应入口或声明时，不自动换协议、回落执行后端或宣传任意兼容。

| 语音转写 | 显式 `openai_verbose_json` 转写绑定 | 需要实际模型与计量协议，估算 token 不是供应商收费结论；转写可用不代表语音发送也已验证 |

## 已选验收方向

维护者于 2026-09-23 选择 **Linux 容器群报告与文件交付** 作为首个验收方向，进一步指定本机 SnowLuma、目标 Linux/amd64 与 Linux/arm64。SnowLuma 作为 OneBot 实现不设固定发行版本兼容名单，按当前源码明确支持的消息协议与 `upload_group_file` 动作及真实回执核对；这不等于任意 SnowLuma 版本无需现场验证。此决定不授权启动、调用模型、改配置或实发，也不是组合已验收或已发布。

准备同一候选版本的材料时，需补齐以下实际值，不填写推测值：

- 源码与同版前端提交，两种目标架构各自的 Linux 系统、容器运行时与 Compose 版本、主服务及所需执行镜像的实际身份；本机双架构构建只供准备，不代替这些现场值。
- 所需模型职责的渠道、模型与请求协议；本机 SnowLuma 的实际连接身份、OneBot 消息／文件动作、上传协议及导出目录映射。若平台报告版本则记入当次记录，但不作为准入或公开兼容名单。
- `group_summary` 的群作用域、时间配置、工作预算和 `render_font_path`；字体／模板来源与分发授权单独核对。实际使用的执行后端、文件目录权限与原发送授权分别确认。
- 原群输入到报告工作的来源／版本／成果记录，以及报告表达的真实回执；文件交付另保留资产身份、上传行动和平台 `data.file_id`。报告或卡片生成不代表已经登记或上传可下载文件，不假定群报告会自动完成文件交付。

首选 Linux 配方的[报告与文件分链前置](../deploy/linux/README.md#首个验收方向的报告与文件)明确主进程字体路径、Gateway 持久产物和 SnowLuma 上传各自的依赖；worker 内的字体不替代报告主进程字体，生成产物不替代平台文件回执。

[SnowLuma 的当前上传群文件文档](https://snowluma.github.io/zh/docs/api/group-file/upload_group_file)同时展示 `{ file_id: string }` 响应形状与 `data: null` 的示例，不能仅凭该页面推断本机返回哪一种。现有适配器对 `data: null` 记 unknown 而非已上传，也不会重传；首个验收须在获准正常上传中记录原行动、脱敏响应与平台 `file_id`。若实际始终不返回该身份，不得把文件交付标为已验收，先按实际协议与回执另行决定处理方式。

尚无本批现场记录；观察材料复用已有发布观察模板。没有以模型名称、渠道品牌或操作系统名单虚填“稳定支持”，所选方向仍需实际观察与已知限制。

## 信任边界

1. **运营面板与根配置**属于受信控制面。群管理员、群内自报身份和模型提案不自动取得运营权限；登录账号保存在主库，业务凭据仍在唯一根配置。面板入口与网络暴露范围由部署者明确配置。
2. **本地插件是受信 Python 代码，不是沙箱脚本。**发现时先导入包，再检查描述符与接口世代；停用开关或 API 世代检查不能阻止包顶层代码执行。公共接口收窄宿主能力的使用合同，不把同进程插件变成安全隔离。只把已审阅且愿意信任的代码放入插件根目录。
3. **工作执行隔离取决于实际部署。**独立 Gateway 可以管理容器，属于更高权限受信服务；worker 不得取得根配置、服务凭据、Docker socket 或控制网。只读挂载、用户映射、出口规则和停止回执需分别确认；页面“就绪”或镜像名不证明隔离已验证。
4. **模型输入和工具资料不改变权限。**原话、网页、文件及角色资料可以影响模型内容，但执行仍受宿主原身份、作用域、预算和 Gate；生成文件不代表平台取得文件，逻辑调用条数不保证底层只有一次传输或费用。
5. **历史记录不是当前可用性保证。**旧连接、旧授权或历史送达不能证明现在仍有效；unknown 不自动重放。保留与恢复限制见[数据生命周期](data-lifecycle.md)。

以上描述既有边界，不是完整安全审计或渗透验收结论。可选后端未取得现场证据时保持未验证，不扩大成“无条件安全”。

## 当前打包边界

| 形态 | 当前配方包含什么 | 不代表什么 |
|---|---|---|
| 源码仓库 | 工程源码、文档、插件参考、已有资源与原许可证／来源文件；根配置和运行产物按忽略规则排除 | 不是已经确认可公开再分发的完整发行包；代码与素材授权仍待决定 |
| Python wheel | pyproject 配方安装主包与内置插件；已构建的 web/static/dist 随包进入，前端源工具链被排除 | 不会自动生成缺少的前端；本地插件、真实根配置、数据库和文件卷需另外管理 |
| Linux 镜像 | Node 阶段新建面板，Python 阶段按 uv.lock 安装非 dev 依赖，运行阶段复制环境 | 不带真实根配置、主库、业务文件、外部插件或 Docker socket；Gateway／执行镜像是独立部署项 |

打包文件依据 pyproject.toml、.dockerignore 与 deploy/linux/Dockerfile；本批没有构建或解包新的发行物，最终候选包内容仍须核对。原资源与许可证不被本页改授其他许可，具体决定沿[授权清点](plan/s0-04-06-license-and-support.md)。
