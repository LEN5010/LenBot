### 4.2 图像参照复用现有媒体路径

业务缺口是“五张角色参照需要能被读取，但不应自动出现在表情候选里”。首批复用 media_assets，不新建图像数据库：参考图以运营素材保存，使用明确的角色参考标签，palette_order 留空；表情库继续沿原表情标签和顺序。参照图只有在用户明确要这类图片时才沿原发送资格处理，日常表情选择不会把它们当反应图。

建议在根配置增加一个小型 `runtime.character_reference_assets` 列表，只保存 `character_key`、`outfit`、实际 `asset_id`。这项配置解决人工确认角色与真实图片资产的对应关系，不保存主机路径，不另建人物权限、版本或相似度平台。保存时在现有登录入口核对素材存在、类型与可读范围；运行只提供五个简短定位项，像素仍由 read_media 与现有图片预算负责。

当前源码已实现这一绑定列表，默认空、最多 40 项，为后续服装版本留出明确上限；人工人物／服装组合与资产分别唯一。素材必须是已登记、启用且独立标记“人物参考”的运营图，固定表情目录在 LIMIT 前排除它。管理入口统一放在媒体页，使用原配置冲突合同；人格页只提供导航。对话实际目录受同场景／global-safe 和总容量约束，只有短定位，没有预载像素。五张附件尚未入运行库，也未保存真实绑定；页面和辨认效果仍待同版实际验收。

实际群图先按原流程提供。需要指认人物或区分候选时，主对话按需读取相关常服图，同轮比较实际像素。普通看图闲聊可以回应已看清的动作与内容；没有必要点名时不强行补人物名字。首次不能确定的图片可读两个人物的参照或询问一项必要信息，不增加专门的识别模型、自动重试或评分系统。

每轮不固定加载五张参照，也不把全部图集常驻为像素。角色定位表可稳定存在，读到哪张图仍由原 manifest 记录，服装变化和缺少细节的图片保留实际未确认部分。

### 4.3 纠正必须带着对象采用

“这是贝拉”首先沿真实 reply 关系定位到被纠正的图片和旧回答。下一次仍讨论同一来源或同一已登记资产时，把纠正原话、其指向的图片及当前问题作为同一个相关材料包带入，优先于旧回答；不把一句没有对象的“曾经认错了”塞入长摘要。

这里增加的是现有相关来源装配中的对象关联，不新增长期状态表。跨图片泛化由稳定角色资料与已读参照支持，单次纠正不自动改写某个人物的全部外观。若运营确认某资产人物标注有误，在现有素材编辑入口改标签及说明，并保留来源记录。群友长期称呼和偏好仍沿 remember/refute/supersede 的原认识账本处理。

首批不自动从“看错后道歉”抽取全局人物知识，也不把每次视觉判断写成长期事实。需要持久化的群内认识仍有具体主体、真实原话与修订关系；短期纠正已经足以解决的，不额外调用维护模型。

当前源码已接入初始对话与续轮新输入：同场景、截点内沿实际引用、Bot 已送达回执的主来源／覆盖来源及同一资产定位相关原话。人类新说法在取舍时先于旧回答，仍经原文字／像素预算和阅读确认；image_discussion 目录只标真实关系，不自动判断谁说得正确。追溯和后续回复使用原检索限额，达到限额明确标注；未明确引用和取得新资产 ID 的重传图片不自动绑定旧纠正。原事件表新增两项定向引用索引，没有纠正表。查询、装配和下一句采用效果尚待正常业务验收。

## 5. 减少八股和机械感的行为合同

保留现有表情强度与角色活力，调整的是“如何接住这一句话”。普通聊天按对方的情绪、对象和上一句接话，技术任务按实际结果表达；不强制两类场景使用同一套结论、理由、建议、追问结构。

| 场景 | 期望行为 |
|---|---|
| 闲聊、接梗、轻微吐槽 | 自然回应或旁听；可以只有一句话、一张合适表情或短图文。 |
| 对方明确问问题 | 把问题处理掉，角色口吻作为表达风格，而不是转移话题的理由。 |
| 已有足够资料的短问答 | 直接给需要的内容，必要时短附来源与适用时间。 |
| 对方催促、表达不满 | 说清当前已经完成的事和卡住的一步；有可提交结果就提交。 |
| 收到纠正 | 先在下一句采用正确对象或说法；道歉长度随实际影响，不以“永远记住”代替修改。 |
| 工具或部署暂不具备条件 | 说明具体缺项、已经保留的成果和可执行下一步；文件没有交付就保留未完成项。 |
| 话题结束 | 自然收住，按原观察期限旁听。 |

固定合同用“选择什么、输入来自哪里、做到什么就结束”的正向表述。事实资料、操作协议与角色语气各自放在所属位置。必要的参数约束由 Schema、字段说明和宿主校验承担，减少大段反复提醒；不建立群发后的自动改写器、禁词表或“像人评分”。

表达不靠虚构经历增强亲密感。对歌曲的喜欢可以表达为当下评价；已看、已听、已做等状态沿实际观察和工具记录表述。表情频率保持原设置，选图跟随语境；回应严肃催促时优先解决事情，不用可爱语气把问题带过去。

现有 own_recent_expression 继续提供本群近期表达提示，不扩建重复句指纹或全局话术库。人工样例如确有必要调整，先给逐条预览，由用户确认后再保存。

## 6. 提交协议：减少填单返工，保留执行边界

### 6.1 普通回复只承担必要字段

首批保留 respond 名称、现有提交事务与消息预算。普通回复以 segments、真实回应来源与可选展示引用表达；intent 优先由唯一业务句柄确定，避免同时让模型填写 intent 与一组可能互相矛盾的关系字段。创建确认、操作确认、成果交付、工作说明和文件仍保持互斥，宿主从真实回执和工作版本派生内部结果。

资料性回答才提供依据。闲聊可完全省略 answer_basis；显式 social/general 的 Schema 不接收证据数组。observed、work_result、mixed、unverified 分别提供其合法字段组合，不把所有属性平铺成“看起来都能一起填”。公开 Schema 与本地模型使用同一份业务定义，避免两个手写版本漂移。

错误返回定位到具体 messages 索引、字段及真实非法组合。合法内容保留在当前轨迹中供修正；宿主不悄悄删字段、换类别或把不合法的整批提交当部分成功。

### 6.2 一条回答可以明确覆盖多条普通来源

实际群聊经常把连续两条问题合在一句回答。建议给普通消息增加显式 `covers` 来源列表：`source` 仍是主回应与授权身份，covers 声明同条消息还回答了哪些已读、同场景、当前待处理来源。宿主逐项检查可读范围、待处理身份与原回复资格，再生成原内部 SourceOutcome。文件、控制、新委托的请求者仍由唯一原业务来源确定，covers 不改变其归属或权限。

对应地，公开 sources 只要求模型说明本阶段没有被消息或实际提案覆盖的去向，如 silent、incomplete；与已提交消息明确关联的 replied、与实际创建提案关联的 delegated 由宿主生成。等待仍由真实 expect_reply、next 与送达回执建立。这样减少两份列表各自猜测的一致性负担，同时保留显式多来源声明；仅仅读过的消息不会自动变成已回复。

这是本计划中一项定向接口变更，针对 21 次实际来源关系拒绝。公开 Schema、解析模型、ProposalLedger 与来源投影需要同批核对，并核对原提醒、工作完成与插件系统来源。现有页面已经使用 SourceOutcome.action_ids 支持多来源关联同一行动，本批复用这条投影，不额外改 Vue。历史事件与 Trace 继续按保存的事实展示，不回填旧处理状态；不保留两套自动猜测参数的兼容入口。效果仍待同版正常调用确认。

### 6.3 引用已展示资料，减少手写坐标

建议在已有资料页投影中增加短 `evidence_ref`，在本轮引用对象内映射到实际 result_id、坐标单位与已提供范围。answer_basis 选择已有页引用，宿主解析为原 ResultSpan；模型不再为“已读这一页”手填四个字段。它是现有 TurnReferences／资料展示的局部映射，不是新证据数据库或内容指纹。

当前源码已在资料展示工具包中实现该局部映射，使用 E 开头的不透明页名；对话 answer_basis 和普通工作 finish_work 的公开输入使用 evidence_refs。工作原 observation_reads JSON 在坐标单位下保存页名到范围的映射，支持恢复与独立插件读取回传；实际 ResultSpan、工作状态及公共兴趣候选的原范围结构保留。旧阅读记录没有页名时不回填，按现有工具读取需要的页后取得引用。

只有最终请求实际保留、模型返回后确认提供的页可获得引用资格；跨工作恢复从现有 observation_reads、原资料和检查点重建，未读页不补资格。引用已读整页可以减少错误范围，但仍不证明该页支持每个结论；模型应围绕问题读到对应段落，内部引用不代替必要的群内来源说明。

原角色资料和人物参照继续作为运营参考，不因此变成人类原话或最新外部事实证据。

### 6.4 分阶段提交实际进展

短查询已有答案、后台工作也已形成合法创建提案时，及时使用现有 checkpoint 提交，不等待其他闲聊来源也整理出完美答案。已提交阶段沿原消息、预算和回执继续，不重发、不撤回；没有新增可交付内容时不固定发“收到、正在处理”。

单条独立参数错误仍不能穿透同一事务。先通过减少冗余字段与明确来源关系降低错误率，再评估是否还有实际批次边界缺口；不先拆出第二套提交系统或提高三条消息上限。

## 7. 能力调度：先完成问题，再决定执行方式

### 7.1 使用现有循环和工作框架

保留对话、长期工作、插件和维护的当前职责。短查询、计算与少量资料续读在原对话预算完成；需要较长执行、持久进度、产物执行或仅工作可用工具时创建原工作。已完成研究追加格式转换时，复用成果资料，不重新研究。

本批不接入外部执行循环或另一套子代理框架。已有只读工具并发保留；提案、工作状态和有顺序依赖的工具仍串行。若后续有实际可独立分解的工作，再使用已有插件工作入口，并共享原工作来源、权限、累计预算和回执，不让子工作重复购买预算或向群里各自发言。

### 7.2 能力事实能指导下一步

复用 runtime_facts.capabilities 和 tool_search，把当前状态区分为：可直接读取、可委托工作、等待具体前置、取得资料但尚未展示、已生成但尚未交付。字段由原配置、部署、授权和回执投影，不让模型从“工具名存在”推断可执行。

源码已补齐混合模块的对话／工作用途、条件型工作用途、入口缺项与工作开关／模型前置；沿原能力卡显示同一投影。tool_search 在排名和数量限制前应用原插件／工作工具子集，嵌套展开目录与父入口分开，不改变实际权限、阅读账或预算。条件型用途仍由真实工作中的原入口核对，具体调度效果和页面呈现待验收。

工具说明只描述用途、适用条件、重要输入与返回含义；实际对象、句柄和额度放到运行事实与回执，不把本轮目标写进 Schema。按需发现后保持同轮定义，不因进入终结阶段就随意换目录。

已知官方地址且搜索没有有效线索时，直接使用已有 read_page；搜索目标发生有理由的变化才换查询。当前工具失败保留具体原因，原循环选择下一步，避免机械地改几次同义关键词。需要阅读的资料以完成问题所需段落为准；已有 next_call 用于本地续读，source_next_call 用于下一批源端资料。

### 7.3 未完成事项要有准确结果

查不到、没读到、未执行、未生成、未上传分别沿原结果状态保留。公开回应可以简短，但内部来源去向应有对应 unfinished，不能用一句拒绝或安抚把整个需求记成已完成。已有失败不自动获得新一轮无限重试机会；继续、修订与恢复沿原明确来源和预算处理。

## 8. 相对时间与回忆语义

业务缺口是同一问题重跑时“最近十分钟”被重新解释。建议将原话回忆的时间参数整理成显式两种输入：绝对区间；相对于某条已读请求来源的回看区间。相对区间由来源 M 和回看秒数组成，宿主以原事件 timestamp 计算起止，业务时区用于日期含义与展示。两种形状互斥，入口解析一次，不猜缺失字段或自动把错误绝对时间改成另一个问题。

第一次执行在原工具记录中保存解析后的区间和锚点，后续同一来源的重复处理继续使用原锚点。返回结果显示实际区间、人物、场景和截点，模型据此回答。按资料原身份复用查询结果时仍须重新提供正文，不继承未取得的阅读资格；新提问明确要“现在再看”时才使用新来源的时间。

精确人物／时间／特殊字符查询以原话命中为结果主体。摘要只是有需要时的主题定位；不为每次单字符查询夹入一批不符合人物时间条件的摘要。保留已修复的 SQL 筛选顺序与 LIKE 转义，不扩大 LIMIT、不新建搜索框架。

## 9. 300k 上下文与压缩预算

### 9.1 建议值及实施顺序

| 项目 | 当前观察值 | 待验收建议 |
|---|---|---|
| 对话总上下文 | 200,000 | 300,000，作为估算容量上限 |
| 对话输出预留 | 4,096 | 首批保持，长报告沿工作与文件表达 |
| 近期原话文字预算 | 130,000 | 首批保持；先让新增知识与当前资料有空间，不同步扩大旧历史 |
| 历史候选条数／锚定步长 | 1,500／1,000 rowid | 首批保持，不与资料接入同时改变 |
| 工作总上下文 | 64,000 | 单独候选 128,000，观察正常长工作的压缩次数和耗时 |
| 工作输出预留 | 16,384 | 首批保持 |
| 图片张数／字节 | 6／3,000,000 | 保持独立约束，按需选择参照像素 |

这些值是计划建议，尚未写入根配置。总上下文同时容纳系统与角色文字、工具定义、消息、工具结果及图片估算，并预留输出；不是把近期历史文字额度直接设成 300k。模型宣称支持 1M 是容量线索，实际职责绑定、接口协议与请求限制仍须核对；不能单靠型号标签宣布已验证 300k 请求。配置通过现有面板保存，重启及手工文件操作按运行手册进行。

先完成协议和资料接入，再分开改变工作与对话容量，记录每次变更时间。工作窗口增大还可能影响 token 预占和日额度准入，必须沿原资源账核对；不同时调高轮数、工具数或日额度来掩盖回归。

### 9.2 装配次序与常驻内容

固定人格和已确认角色资料保持稳定前段；近期完整原话保持原时序和锚定；当前关联原话、明确纠正与已读图片按原带回位置提供；运行事实、预算和工具结果各自沿现有位置更新。新增资料不把旧关联消息搬回窗口头，不插入动态时钟或本轮 ID 到固定角色事实。

六份文字的整理稿可整体常驻，无须先做复杂检索；完整图集与全部像素按需读取。把三十万当作总容器，先保证当前请求和实际依据，再装可选历史；不为了缓存比例扩大到无关旧事压住当前问题。

### 9.3 先测量已有实际路径，再改性能热点

沿现有阶段记录补齐 event_packing 内文字投影与媒体准备的归属，复用同一次准备结果，不额外读取群消息或调用模型。已有初始装配 39 秒的观察值得处理，但不能先断言深拷贝就是唯一原因。每轮最终容量与已读重建保留，局部估算优化不代替最终核对。

源码已增加 event_packing_detail，记录真实装配中的投影、快照／回退、容量估算、媒体准备与可选释放，以及媒体资产查询、源准备和局部复用次数。同候选未改变时少做一次完整估算；释放可选材料后重算，最终容量与阅读核对保留。自动装配复用前若资产已不可用，不再使用旧局部像素。新统计尚未实际运行，没有延迟改善结论；详细口径见[上下文诊断](context.md#7-缓存与诊断边界)。

工作优先复用已保存资料并按问题读取正文，原生交换和检查点继续按原 WorkCompressor 外置／压缩。扩大工作窗口后观察同类正常工作的压缩成本，再决定是否调整 trigger/target；不同时更换压缩策略、模型和阈值。压缩摘要只保留任务连续性，证据继续定位原资料。

缓存统计固定拆成正数、显式零、缺失。客户端重试、中转行为、窗口跨界、工具变化和新的资料版本分别记录；请求改了提示词和工具定义后重新形成观测基线，不与旧版本直接混算。

## 10. 文件交付形成可完成的路径

先在现有能力页给出文件生成、持久资产准备、平台上传三段真实状态。当前 onebot_file_upload.deployment_verified=false 的前置由运营核对实际实现、版本与只读挂载后确认；这不是可以为通过验收直接翻转的开关。真实申请者、群范围、发送授权和工作修订继续逐项核对。

研究过程中明确要文件时，原工作在既有执行环境生成产物，登记为当前版本的 file_asset，再由对话提交上传，最终由真实 file_id 完成交付。研究已经完成后追加文件时，创建仅做格式转换／导出的工作，复用原 result_refs 和委托关系，不重新搜索，不把已完成旧工作伪装成可恢复状态。

当前源码在普通 start_work 增加 reuse_work_ref，选择已实际提供的普通研究成果版本；原事务核对版本与真实结果，将固定的结果输入保存在新工作 payload.reused_work，并带入对应资料身份。原 Gate 与 provided_work_results 继续核对已读资格，新工作不会继承旧 observation_reads、额度或发送资格。工作页已增加原／后续工作关系及固定输入展示。专用插件结果继续沿所属业务入口处理；没有新增跨插件复制权限或通用子工作平台。工作初始事实已接入现有 file_delivery_facts，实际生成、登记和群上传仍分别待验收。

首批以现有 TXT、CSV、PDF 等支持格式落地。独立 `.md` 如纳入本批交付，只作为“纯文本 Markdown 文件”的定向格式扩展，复用文本内容检查，并在实施前明确列入该批变更；不是开放任意扩展名或可执行文件。原工作与新导出工作的身份和成果关系在面板可追溯。

本批已明确纳入独立 `.md`：源码使用 text/markdown，复用原 UTF-8、控制字符和大小检查，不渲染或执行正文。文件准备的部署、授权、修订、额度与回执路径均保持原样，源码支持尚不等于真实文件已经成功交付。

群内正文优先短说明和必要结论，详细对照表沿文件交付，避免把大段 Markdown 表格直接刷到群里。生成成功、资产可下载、提交上传与实际 file_id 分别显示；上传未知继续保持未知，不自动补发。前置缺失时给出具体缺项并保留文件要求的 unfinished。

## 13. 人工验收清单

下表描述要观察的正常行为，不提供脚本、伪造数据或自动回放。选用真实原话、真实问题和已授权群范围，保持同版，保存来源 ID、调用 ID、具体结果和必要未确认项。

| 编号 | 正常场景 | 通过证据 |
|---|---|---|
| A01 | 日常接话、接梗、对方互聊和明确收住 | 保留用户认可的活力与表情倾向；说话对象正确，该停时能停，格式自然 |
| A02 | 当前人物归属、别称与常服问题 | 直接使用确认的当前口径；群友身份和角色身份各沿实际对象 |
| A03 | 用户提供的常服图及正常群图 | 原图与需要的参照实际提供；输出与图中细节相符；未看清时不强行编名字 |
| A04 | 正常发生的一次人物／对象纠正 | 下一句采用纠正，同一对象再次出现时仍关联原纠正；不把道歉当作持久处理 |
| A05 | 两条连续问题可以合并回答 | 同一消息显式覆盖相应来源，内部处理结果与实际回应对应；无关未完来源保留 |
| A06 | 闲聊与有资料的回答各一例 | 依据类别与结构一致，不因重复元数据反复提交失败；真实非法来源仍被所属边界拒绝 |
| A07 | 有明确人物及相对时间的原话回忆 | 起止区间相对原提问固定；续轮／重新处理不会移动为另一个时间窗口 |
| A08 | 当前事实查询和已有本地资料续读 | 工具取得、正文已读与最终引用对应；已知来源可直接读取，查询没有机械重复 |
| A09 | 短问答与一个正常长工作 | 短问题及时处理；长工作只有真实创建后才确认，已有成果不会为重发而重新研究 |
| A10 | 已有成果追加文件 | 只做需要的导出；执行、资产、上传及真实 file_id 逐项可追溯，阻断保留 unfinished |
| A11 | 正常工作资料增长／压缩 | 保留原目标、预算和已读依据；压缩次数与耗时可读，未取得资料不被摘要补成已读 |
| A12 | 新表情与人物参照的素材页 | 19 个文件逐项登记结果明确；五张参照不混入反应表情；启用、顺序、保存冲突可理解 |
| A13 | 偏好修订、普通提醒改期／取消 | 现有认识与提醒链路仍正确，已取消事项不因界面或新资料重新激活 |
| A14 | 能力、参数、工作和来源页面往返 | 原对象与返回位置清楚；保存状态、运行状态、送达状态分别准确 |

效果目标首先是消除普通回应中可避免的依据类别与来源对应返工，而不是要求模型永不出错。新运行继续报告 invalid_arguments 的类别及涉及 episode 数、调用与本地装配耗时、真实交付延迟；遇到外部链路错误单独记录。未出现的恢复、未知送达等场景保持未覆盖，不为补齐表格制造故障。

## 14. 发布、回退与验收决定

本次已确认的方向已进入按批次持续实施。首批资料稿、素材名称与人物绑定仍先预览；实际配置、运行素材导入、上传部署核验与真实群发送各沿当次授权。接口实际上下文上限、工作额度预占是独立前置，某一项未就绪时不阻塞其他源码工作或资料整理，也不伪造完成。

发布沿原停机与备份手册。代码问题通过后续修复或明确的回退提交处理，不重写 Git 历史；运行设置从原面板恢复已保存的前值。资料停用只改变采用与选择，原稿、原事件、旧 Trace、旧工作和已交付回执保留。表情与参照的退出采用现有禁用和配置绑定移除，不删除用户原文件。

验收仍分别确认四点：提交接口的定向简化及实际效果；人物事实与五张图的采用方式；对话 300k／工作 128k 的分批候选值；文件链路完成条件。按 N00—N06 记录源码进展与运行结论，不把本计划、源码改动或已保存的五张图当作线上能力已经生效。
