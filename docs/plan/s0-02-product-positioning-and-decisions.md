## 一、产品定位（一页）

**LenBot 是面向长期多人群聊的 Agent Bot 框架。它持续理解互动，按需调用工具和推进事务，
并让来源、成本、执行与实际送达可追溯。**

默认发行版可直接安装使用，而不是只给开发者一个 SDK；具体人格、嘉然素材、直播、日历等
可被替换或关闭，不应成为理解内核的前提。

| 使用者 | 真正需要的结果 | LenBot 的承诺 |
|---|---|---|
| 群成员 | 能接住问题、理解补充和纠正；不无意义插话 | 连续互动与有分寸的参与 |
| 委托任务的人 | 工作跨越几轮仍记得原目标；修改、取消和交付有实际作用 | 持久工作与明确的实际状态 |
| 运营者 | 知道为什么没回、查了什么、钱花在哪里、是否真的发送 | 可追踪、可解释、可管理 |
| 插件作者 | 不学习全部内核也能增加业务能力，升级不会无故失效 | 小而稳定的公共接口 |
| 新部署者 | 不找作者远程代装，也能运行、备份、升级和报错 | 有范围的稳定发行版 |

### 首个稳定版本范围（建议）

以 **QQ 群聊的一条明确适配链 + 实际核验的模型协议／渠道组合**为起点。支持群聊、
按需检索与计算、跨轮工作、真实消息／已选文件交付、插件扩展和审计查询。

### 非目标（首版不进入稳定门槛）

多平台、跨群个人记忆、独立进程插件、外部 Harness、复杂账号自动化。已有可选功能保留，
但分别记录「未启用／未部署／待验收／已确认」，**不因为代码存在就扩大稳定范围**。

### 不作为核心承诺的说法

不将「比传统框架更 Agent」「250K 上下文」「97% 缓存率」作为核心承诺。它们要么是比较
口号，要么是实现选择或运行指标，不能替代用户结果。

### 与当前基线的实际关系（只读核对）

`pyproject.toml` 当前 `version = "0.1.0"`、`description = "Add your description here"`、
无 `LICENSE`、无 `CHANGELOG`、无发布标签。产品定位当前只存在于内部计划中，尚未反映到
项目元数据。这属于 S0-04 / S5-06 / S6-03 的待办，不在本任务内顺手改。

## 二、决策一：会话连续性 — 普通群聊延续什么

**问题。** 当前普通对话是否从「逐轮重建请求」推进到「会话段」？

### 现状（只读核对）

- 没有「会话段」这一持久对象。持久表清单里没有 segment 表；
  `scene_sessions`（`src/len_bot/events/store.py:102`）是 **scene 级** 单行状态
  （`scene_id TEXT PRIMARY KEY, version, last_observed_event_rowid,
  attention_scanned_event_rowid, state_json, updated_at`），不是会话段。
- `episode_id` 存在（`src/len_bot/scenes/actor.py:32`），但它是**执行 episode** 的身份，
  用于租约（`acquire_episode_lease`，`actor.py:93`）、检查点事件
  （`turn:{episode}:checkpoint:{index}`，`actor.py:294`）和提交归属，不是上下文段的身份。
- 历史压缩侧存在 `history_batches` / `history_origins` 两张表，说明压缩批次与来源已有权威记录。

**路线书设计（第 4 节）。** 四层身份：一个群一个主会话；主会话有多个顺序衔接的
**会话段**；段内多次**运行**；一项长期**工作**有独立执行轨迹。段内尽量追加原话、工具交换与
真实结果；容量不足或人格／模型／协议／工具集合大变时换段，换段原因进入 trace。
压缩交接分两部分：模型压缩的语义摘要 + **宿主确定性附带的未完事项**（必须来自权威状态，
不由摘要模型猜测；摘要不能创造或结束任务，也不能重置额度）。

### 建议采纳

采纳会话段合同，但**先设计后实现**，且不新增 transcript 表：能够在不可变事件与工具结果上
还原的部分优先复用原记录。

| 必须回答 | 建议答案 |
|---|---|
| 谁拥有状态 | 段关系与截点由宿主拥有并持久化；原话仍以现有事件存储为唯一权威；段只保存装配版本、基础摘要引用与已接入事件截点 |
| 失败怎样呈现 | 「已接入事件截点」不等于「所有来源都处理完」：读过但未回答的请求仍挂在现有待处理集合；部分提供范围必须保留，否则持续会话只会让漏回复更难发现 |
| 何时算完成 | 能解释下一轮继承什么、何时换段、压缩保留什么、恢复为何不重做外部行为 |

### 否决的替代方案

- **把所有原话复制进新的 transcript 表**：与「每种事实只由一个地方拥有」冲突，且会让
  纠正、权限撤销、资料范围变化失效。
- **靠扩大窗口实现连续性**：长窗口不是状态存储；缓存是收益而不是状态所有者。

### 待维护者确认

1. 是否采纳「会话段」作为正式合同，并把四级身份（主会话／段／运行／工作）写进架构文档。
2. 换段阈值采用「配置容量留出输出与工具结果空间」的具体数值由谁定（根配置，非本任务顺手改）。

## 三、决策二：审计保留与还原 — 每次行为能还原到什么证据

**问题。** 审计材料保存到什么程度？

### 现状（只读核对）

已有可追溯结构，且**不能按更早的待办再次判为未实现**：

- 关联身份：`events`、`model_calls`、`agent_jobs`（含 revision）、`platform_actions`、
  `tool_observations`、`job_exchanges`、`traces`、`usage_reservations` 等表均已存在。
- `answer_basis` 已落地：模型定义在 `src/len_bot/cognition/models.py:154`，
  提案侧在 `src/len_bot/cognition/proposals.py:129` 且有校验
  （`proposals.py:153-156`、`validate_answer_basis` 调用在 `proposals.py:669`），
  宿主解析在 `src/len_bot/events/store.py`，读取面在 `src/len_bot/web/query_service.py`。
- `traces` 表（`events/store.py:154`）以 `kind + scene_id + ref_id + payload` 记录链路。

### 三层承诺（路线书第 5.1 节，建议采纳）

| 层次 | 承诺强度 | 含义 |
|---|---|---|
| 执行可追溯 | **核心承诺** | 能连接真实输入、运行、调用、工具结果、提案、提交、行动和回执；沉默与失败也有真实阶段 |
| 请求可还原 | **有保留条件** | 对实际留存的原文、工具结果、提示／工具版本和媒体引用，能还原请求布局与提供范围；材料已清理或历史缺档时明确显示缺口 |
| 重新运行 | **不在承诺中** | 读取日志不应再次调用模型／工具／平台；相同输入不承诺相同输出 |

### 不可合并的状态（必须保留区分）

```text
模型生成 ≠ 提案通过          提案通过 ≠ 成功发布
成功发布 ≠ 平台收到          文件生成 ≠ 文件上传
搜索命中 ≠ 正文已提供        模型说取消 ≠ 远端执行已停止
缺失 usage ≠ 没有费用
```

### 建议采纳

保留现有表与事务，只澄清「每项事实读哪一份权威记录」；**不新增通用 checksum、内容指纹、
迁移哈希清单、配置签名、备份校验或审计平台**。审计做成日常界面：打开一句回复先看到
关联谁、当前结局、主要来源、是否送达、花费和耗时；没有记录就说没有记录，不让页面
临时调用模型生成「当时原因」。

### 待维护者确认

1. 是否把上述三层承诺与「不可合并状态」写进架构文档作为公开承诺。
2. 保留期限（涉及 S5-03 数据保留合同）：哪些材料按政策清理后只承诺「显示缺口」。

## 四、决策三：插件公共合同 — 第三方可以稳定依赖什么

**问题。** 第三方依赖哪个公开 API 世代？

### 现状（只读核对）

`src/len_bot/plugins/api.py` 是作者入口，当前 `__all__` 实际导出（逐项核对：

`api.py:13-18`）：

```text
BasePlugin, PluginContext, PluginSpec, PluginCallContext, PluginPermission,
PluginType, ToolResult, ToolSource, ToolNextCall, Command, EmptySceneConfig,
ExactText, RegexText, EventType, PluginOrigin, MessageSegment,
BeforeModel, AfterModel, BeforeTool, AfterTool, BeforeCommit, AfterDelivery,
PluginAgentRequest, PluginWorkSpec, PluginWorkRevision, PluginWorkContext,
JobResult, PreparedWorkDelivery
```

共 **28** 个符号（脚本按 `__all__` 逐项核对；与 `api.py:2-11` 的导入完全一致，
无「导入未导出」项）。**没有版本号、没有兼容性声明、没有 deprecated 标记**：
全仓 `api_version` 只出现在两份计划文本中。路线书第 6.1 节要求保留
`plugins/api.py`、`PluginSpec`、`BasePlugin`、`PluginCallContext` 及已存在的工具、事件、
Agent 调用、工作和提交入口，**不重新发明 SDK、不新增重复 manifest**。

### 建议采纳

为公共 API 建立独立世代（例如 `api_version`），插件自身用版本号说明功能变化。
早期不兼容可以明确拒绝并提供一次迁移，不用永久兼容补丁。稳定合同一旦发布，
同一支持范围内不得无说明改变语义。

| 必须回答 | 建议答案 |
|---|---|
| 谁拥有状态 | 宿主拥有身份、范围、预算和归属；插件得到一次调用的明确上下文与必要服务，不直接学 `Runtime`、`ProposalLedger`、完整 `EventStore` |
| 失败怎样呈现 | 错误不静默吞掉后转入另一套默认聊天；取消是控制信号，不等同一般工具失败后继续模型循环 |
| 何时算完成 | 一个目录 + 公开入口 + 清楚版本即可完成读取、事件唤起或后台工作；停用、错误、取消与审计有一致语义 |

### 信任边界（必须如实说明）

当前同进程 Python 插件按「**运营者信任的代码**」处理。缩小 API 有助于防止误用和降低耦合，
但**不是恶意代码沙箱**。以后使用进程隔离主要解决故障和依赖隔离，仍不能自动等同强安全边界。

### 待维护者确认

1. 是否采纳 `api_version` 世代，以及首版世代号与支持政策。
2. 28 个导出符号中，哪些属于「常用能力入口」（建议收窄），哪些降级为内部实现。
   按 AST 核对，**28 个里只有 13 个被任何地方以 `from len_bot.plugins.api import …`
   的方式导入**；其余 15 个（六个 Hook 视图类、`Command`、`RegexText`、`EventType`、
   `PluginOrigin`、`PluginAgentRequest`、`PluginWorkSpec`、`PluginWorkRevision`、
   `PluginWorkContext`、`ToolNextCall`）从未经公共入口被导入。其中一部分是经
   `plugins.work` / `plugins.agent` 等内部模块使用的（例如
   `group_summary/work.py:9`、`cognition/models.py:8`），恰好说明**公共面与内部面
   当前重叠**：同一样本既能从 `api.py` 取，也能从内部模块取，边界未收敛。
3. 公共面已泄漏内核对象：`PluginContext.event_store`（`base.py:97`）、
   `PluginContext.media_service`（`base.py:102`）、`PluginCallContext.ledger`
   （`models.py:34`）。是否在为插件提供限定范围服务的同时收回这些直接引用。
