# S0 前期工作拆分记录

本文件保留 2026-09-21 盘点阶段的工作拆分与后续建议，不是当前执行安排，不要求自动委派。当前范围与顺序见[路线入口](README.md)和[当前任务](../iteration.md)。
它是工作方法记录，不是产品合同；产品合同见[路线书](../LenBot_成熟开源项目路线书_20260921.md)。

## 为什么需要它

路线书第 8.2 节只允许「同时一个共享内核变更 + 一个不冲突的文档／界面工作」。
48 项任务里多数会碰同一批文件（`events/`、`context` 装配、`plugins/api.py`、
`web/routes/`），盲目并行会让两个实施者围绕同一概念各建一套状态。因此委派方案
的第一条不是「怎么并行」，而是**先钉死所有权，再拆分**。

## 可并行性的判据

一份工作可以安全委派给独立执行者，当且仅当：

1. **写集互斥**：两份工作的文件写集不相交（含文档、示例配置、前端页面）。
2. **无共享新概念**：不需要同时决定同一个新表、新枚举或新公共符号。
3. **可独立验收**：各自能用「阅读 + 编译构建 + 获准人工操作」证明，不需要对方的产物。
4. **只读依赖明确**：依赖的现状是只读的，不需要等对方改完才能开工。

读多写少、以核对方主，是当前阶段唯一天然可并行的类型。

## 阶段一（已执行）：只读核对并行

S0-01 要求把 48 项任务与真实符号逐项对照。这属于「读多写少」，可以放心并行。
实际拆成六条互不重叠的读取路径，各写各的报告文件：

| 工作流 | 读取范围 | 独占写集 |
|---|---|---|
| S1 执行主链 | `events/`、`gate`、`actions/`、`call_store`、`web/query_service` | `docs/plan/s0-01-s1-chain-inventory.md` |
| S2 持续上下文 | `context` 装配、`memory/`、`history`、`migration`、`work_context` | `docs/plan/s0-01-s2-context-inventory.md` |
| S3 插件合同 | `plugins/api.py`、`host`、`hooks`、`local_plugins/`、`plugins.md` | `docs/plan/s0-01-s3-plugin-inventory.md` |
| S4—S7 | `attention`、`scheduler`、`cognition/diana`、`web/frontend`、`deploy/`、`.github/` | `docs/plan/s0-01-s4-s7-inventory.md` |
| S0-03 依赖边界 | 全仓 `diana`/`asoul`/bilibili 引用、import 方向 | `docs/plan/s0-03-dependency-boundary.md` |
| S0-04/06 | 许可证、依赖、素材、CI、operations、示例配置 | `docs/plan/s0-04-06-license-and-support.md` |

委派约束（每条都写进了给执行者的提示词）：

- 只读；不改业务文件；不提交；不跑测试、夹具、探针、回放、截图、压力、故障注入。
- 不启动服务、不调用模型或平台、不读业务数据库与媒体内容。
- 唯一写操作是各自那份报告文件。
- 每个结论必须带 `文件:行号`；读不到就写「未确认」，禁止用推测填补。
- 报告末尾附反向引用清单，便于维护者复核而不必重新 grep。

这样并行安全，是因为六条工作流的写集两两不相交，且都不修改运行时代码。

## 阶段二：S1 一条只读解释路径（串行收口）

S1-01 / S1-02 / S1-06 共同描述同一条链路（身份关系 → 请求 manifest → 审计页面），
共享同一批符号。**不并行**，由一个人按顺序做，每步产出一个可观察结果：

1. S1-01 先定身份与阶段术语（语义层，先决定再实现）。
2. S1-02 在已定术语上补请求材料清单。
3. S1-06 把前两步的记录渲染成页面。

若核对结果证明现有字段已足够，这三项退化为查询与页面收口，不改运行时。

## 阶段三：S2-01 与 S3-01 的所有权决策（仲裁点）

S2-01（会话段）与 S3-01（公共 API 版本）都定义新的公共结构。两者可以在**决策层**
并行起草，但不能同时进入实现——必须先由维护者确认「段」与「插件 API 世代」的
所有权边界，再放行实现。这是整条路线唯一的强制串行点。

## 每份委派必须带的内容

无论并行还是串行，委派给执行者的任务都包含：

- **范围**：允许改的模块／文件／公共符号；必须保留的身份、事务、预算、范围、
  回执与配置边界。
- **只读依赖的绝对路径**：包含被引用文档在附件区的只读副本路径，避免执行者
  从对话里猜。
- **禁止事项**：测试／夹具／探针／回放／截图／压力／故障注入；生产启动、真实
  模型调用、真实发送、配置与数据库改动。
- **交付格式**：表格 + `文件:行号` + 未确认清单 + 反向引用清单，禁止套话。
- **验收方式**：只允许阅读、编译构建、以及已获准环境中的正常人工操作。
- **署名约束**：提交信息、PR 正文、代码注释与文档里不出现任何工具、模型、
  Agent 或 CLI 的名字，作者只有仓库所有者。

## 明确不采用的委派方式

- 不让两个执行者同时改同一批内核文件，靠「小心合并」兜底。
- 不让执行者自行决定新增表／状态／公共符号；这些必须先有短设计决策。
- 不为了并行而先造抽象层，再用后面 40 项任务去填。
- 不让执行者以「探针」「回放」等名义绕过当前工程禁限。
