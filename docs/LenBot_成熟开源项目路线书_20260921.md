**规划日期：2026-09-21**  
**源码基线：`9178c34958d0d54843665e56e72012bb3021b644`（master）**

> 核心目标：让 LenBot 从“作者亲自照看的个人 Agent 应用”，成长为“别人能够独立安装、扩展、升级，并解释其行为的长期群聊 Agent Bot”。

## 1. 先决定要成为哪一种项目

### 1.1 建议采用的产品定位

**LenBot 是面向长期多人群聊的 Agent Bot 框架。它持续理解互动，按需调用工具和推进事务，并让来源、成本、执行与实际送达可追溯。**

默认发行版应当可以直接安装使用，而不是只给开发者一个 SDK；同时，具体人格、嘉然素材、直播、日历等可以被替换或关闭，不应成为理解内核的前提。

不将“比传统框架更 Agent”“250K 上下文”“97% 缓存率”作为项目的核心承诺。它们要么是比较口号，要么是实现选择或运行指标，不能替代用户结果。

| 使用者 | 真正需要的结果 | LenBot 应当提供的承诺 |
|---|---|---|
| 群成员 | 能接住问题、理解补充和纠正；不无意义插话 | 连续互动与有分寸的参与 |
| 委托任务的人 | 工作跨越几轮仍记得原目标；修改、取消和交付有实际作用 | 持久工作与明确的实际状态 |
| 运营者 | 知道为什么没回、查了什么、钱花在哪里、是否真的发送 | 可追踪、可解释、可管理 |
| 插件作者 | 不学习全部内核也能增加业务能力，升级不会无故失效 | 小而稳定的公共接口 |
| 新部署者 | 不找作者远程代装，也能运行、备份、升级和报错 | 有范围的稳定发行版 |

### 1.2 三项需要被验证的差异化假设

**连续性假设。** 以群场景和持久事务为中心，比把每条消息单独处理，更能减少丢上下文、重复查询和任务归属错误。这必须通过真实互动观察证明，不能凭长窗口推导。

**可解释性假设。** 把观察、生成、提交、发布、送达分开并连接证据，会降低用户排障成本和虚假“已完成”的风险。是否达到目标，应当看真实失败能否定位，而不是日志行数。

**可组合性假设。** 让普通命令、模型工具、业务事件、长期工作共享调用、计量和提交路径，可以让插件扩展不破坏整体连续性。是否达到目标，应由外部作者开发真实插件证明。

这些并不是其他项目不可能实现的独占技术。开源项目可以因为取舍清楚、默认体验完整、维护方式可靠而值得存在；不需要先证明所有同行落后。

### 1.3 首个稳定版本的范围

建议以 **QQ 群聊的一条明确适配链＋实际核验的模型协议／渠道组合**为起点。支持群聊、按需检索和计算、跨轮工作、真实消息／已选文件交付、插件扩展和审计查询。

多平台、跨群个人记忆、独立进程插件、外部 Harness、复杂账号自动化，不默认进入第一版稳定门槛。已有可选功能保留，但分别记录“未启用／未部署／待验收／已确认”，不因为代码存在就扩大稳定范围。

## 2. 本次研究如何改变路线，而不是增加功能清单

### 2.1 对比较对象的校正

当前 AstrBot 的官方文档已包含 Agent 执行器、工具、技能、子代理、主动能力和上下文压缩等内容；MaiBot 当前 SDK 也提供工具、Hook、消息网关、LLM 接口、主动任务和独立开发边界。不能继续用“没有工具调用、只是 chat 函数”概括它们。[R07][R08]

普通 API 函数调用只是模型接入方式。架构上的真正问题是：持续状态归谁、谁选择行动、工具结果是否进入下一步、任务是否跨轮存在、外部结果是否被真实记录。

### 2.2 应学习的管理与开发范式

| 参考 | 已核对的做法 | LenBot 采纳什么 | 不照搬什么 |
|---|---|---|---|
| AstrBot 贡献指南 | 界面变更、操作文档、旧→新入口和变更日志要求同步；功能和无关布局重排应分开 | 同一 PR 同步代码、界面、文档、样例及迁移；减少反复挪界面 | 不照搬其全部验证命令、English-only PR 约定或大型功能面 |
| AstrBot 插件文档 | 提供最小实例、分主题开发文档和发布流程；有宿主版本兼容声明 | 插件 API 明确版本，样例跟随发行版，作者能判断兼容范围 | 不新增重复 manifest，不立刻建设市场后端 |
| MaiBot 当前 SDK | 作者通过 SDK 与 ctx 取能力，不直接导入主程序内部模块；有生命周期和工具／命令区分 | 公共入口和内部实现分开；简单命令不强制经过模型 | 不照搬独立 Runner、IPC、配置来源和全部组件类型 |
| MaiBot 工程约束 | 会话身份由注册／管理链提供，业务模块不能自己猜身份；反对 fallback 掩盖问题 | 宿主绑定场景和主体；错误在真正边界暴露 | 不用复制目录或函数名字作为“框架化” |
| MaiBot 贡献文档 | 区分核心功能、问题修复、文档与适合插件的小众需求 | 核心能力变更先确认范围；业务需求优先插件 | 该文档自标 2025-04-05，不能把其中多人评审门槛照搬给单人项目 |

上述分别据 [R06]—[R10]。这些是公开文档中的要求或接口，不是对它们全部实际流程执行效果的独立审计。

### 2.3 Agent 工程资料提供的原则

上下文工程资料强调压缩、按需取得信息和将长任务材料留在子工作内，而不是不断把所有内容填进主窗口；提示缓存官方文档则说明稳定前缀与工具定义的重要性。这两者共同支持“有效连续性优先，缓存是收益而不是状态存储”的路线。[R11][R12]

链路追踪中的父子关联概念可用于现有 run/call/job/action 记录，不意味着需要立即部署完整遥测平台。[R13]

### 2.4 当前项目已有什么，不能重复建

本次 HEAD 仍为 `9178c34`。该提交说明区分了编译／构建通过和人物素材、真实页面、交付与性能尚待同版验收；本书没有运行生产或模型请求。[R01]

当前架构文档明确存在 SceneActor、原生 AgentLoop、ProposalLedger/Gate、持久工作、发送账本、调用计量和插件入口。普通对话仍逐轮重建请求，长期工作保留原生检查点。固定工具结构、`answer_basis` 和群工作台等已经有源码改造，不能根据更早的待办将其再次判为未实现。[R02][R03][R04]

仓库原总计划已定义 U01—U10、B01—B12、M01—M24、P00—P11 和 A01—A30。本路线是产品化里程碑，不建立第二套内核或与其竞争的状态清单。[R05]

## 3. 目标架构：明确所有者，而不是堆更多层

```text
平台适配器 / 感知插件 / Scheduler
                 │
                 ▼
     原始事件 + 场景归属（现有 EventStore）
                 │
                 ▼
       SceneActor / 注意力机会
                 │
       ┌─────────┴─────────────────┐
       ▼                           ▼
 确定性插件服务              SocialCognitionCore
       │                   普通群聊持续上下文
       │                           │
       │                        AgentLoop
       │                   读取 / 计算 / 委派
       └─────────┬─────────────────┘
                 ▼
     ProposalLedger + RuntimeGate
           持久事务确认
                 │
                 ▼
        发布 / ActionQueue / 平台
                 │
                 ▼
          真实回执回到场景

长期工作：现有 JobStore / JobRunner / WorkContext
           │  独立执行轨迹、原预算与目标
           └──进度/成果事件→原场景→统一提交与交付

审计：关联已有事件、请求材料、调用、工作、提案和回执
界面：通过现有 QueryService 读取，不拥有另一份业务事实
```

上图是对现有主链的目标收敛，不是要求将已有实现全部改写成图中的新服务。已有关键所有权与事务边界见 [R02]。

### 3.1 内核、策略、预设的边界

**内核机制**负责身份、作用域、时序、持久状态、工具执行、额度、事务、回执和错误含义。这些不能由模型或插件靠提示词重新解释。

**默认策略**负责何时观察、何时发言、短查询与长工作如何选、如何压缩、是否主动研究。它可以有明确取舍，但不需要立即抽象成可插拔策略语言。

**个人预设和业务插件**负责角色、素材、关注对象、日历、直播和站点服务。嘉然机器人保留为主要参考发行版，同时增加一个不依赖这些业务的通用配置。

只有为了具体场景减少真实耦合，才移动代码。先明确依赖方向，不进行“为了像框架而拆包”的大重构。

### 3.2 每种事实只由一个地方拥有

| 对象 | 权威所在 | 不能由什么替代 |
|---|---|---|
| 群里发生过的原话与事件 | 现有事件存储与真实平台身份 | 摘要、模型复述或生成草稿 |
| 当前观察、来源处理和短期互动 | SceneSession 与现有来源状态 | 一个笼统的 last_seen 游标 |
| 已提供给模型的经历 | 当前会话段／请求 manifest／完整工具交换引用 | “搜索到了”或“工具注册了” |
| 未完成目标与执行进度 | 现有工作、等待、提醒和提交状态 | 模型在摘要中写“已经结束” |
| 长期认识和修订 | 现有单一知识账本 | 第二份个人事实库、向量索引 |
| 外部行动结局 | ActionQueue 与真实回执 | 模型说已完成、HTTP 请求开始 |
| 参数与密钥 | 根配置及原配置锁／凭据机制 | 环境变量、插件自建配置或数据库覆盖 |

这不要求将所有已有状态强制改成从事件完整回放。保留当前数据库与事务，只澄清每项事实应读哪一份权威记录。

## 4. 第一份核心合同：普通群聊究竟延续什么

### 4.1 建议：持续的是“经历＋未完事项”，不是所有 Token

主会话需要延续近期群聊、谁在向谁说话、模型已取得的必要材料、进行中的澄清与工作，以及系统实际上说过和做过什么。

不同内容采用不同生命周期：

| 内容 | 延续方式 | 何时不再占主窗口 |
|---|---|---|
| 近期原话、引用关系、必要原生交换 | 段内稳定追加 | 换段后保留必要近期片段，其余可定位 |
| 正在处理的请求／等待／工作 | 宿主绑定真实状态和来源 | 被实际完成、取消、过期或明确结束 |
| 临时注意力与参与窗口 | 现有 Session 限时投影 | 到期后自动不再作为当前注意力 |
| 大网页、长脚本输出与文件 | 原结果／资产存储，主窗口放适用部分与定位 | 详细材料留在工作轨迹或按需回读 |
| 摘要与长期认识 | 原历史／记忆系统，保留来源和版本 | 修订、失效或按保留政策清理 |
| 时钟、额度、当前资格 | 本次运行事实 | 不作为长期认识反复累积 |

### 4.2 四层身份

一个群有一个主会话；一个主会话可以有多个顺序衔接的**会话段**；一个会话段里可以有多次**运行**；一项长期**工作**有独立执行轨迹。

```text
群场景 A
  └─主会话
      ├─会话段 1：基础材料 + 连续追加的经历
      └─会话段 2：延续摘要 + 必要近期原文 + 新经历
          ├─运行 n：短查询与回复
          └─工作 J：原目标/revision/预算/检查点，独立执行
```

这里的“会话段”是推荐的新逻辑合同，当前普通对话文档并不等同于已经实现它。建议先复用现有存储和完整交换工具，新增字段或表必须说明具体缺口。[R03]

### 4.3 一个会话段最少需要知道什么

逻辑上需要：所属场景、段身份、装配／提示与能力定义版本、基础摘要引用、已接入事件截点、完整原生交换引用及其实际结果关联。

这些是设计字段，不是要求一次新增一套数据库。禁止把全部原话复制到新的 transcript 表；能够通过不可变事件与工具结果引用还原的部分，优先复用原记录。需要保存的供应商原生续接字段由现有协议层负责，不手工丢弃或通用化猜测。

**已接入事件截点不等于所有来源都处理完。** 读过但未回答的独立请求仍然挂在现有待处理集合；部分原文的提供范围也必须保留。否则“持续会话”只会让漏回复变得更难发现。

### 4.4 段内追加与换段

一段内固定系统／人格的具体版本及基础历史；后续尽量追加原话、工具交换和真实结果。应用每次从数据库重新渲染，只要得到一致表示，同样可以符合这份合同，不要求持有某个内存列表才算连续。

在容量即将不足、需要结构性更换人格／模型／协议或合法工具集合大变时换段。容量为当前模型与通道配置留出输出、工具结果和必要状态空间，不固定承诺 250K；换段原因进入 trace。

权限撤销、资料范围变化和重要纠正优先于缓存。旧工具即使还显示在历史中，执行时仍使用当前资格；不该再提供的资料不能为了稳定前缀继续进入下一次请求。

渐进工具发现可以合法改变工具定义或工具集合。不要为了追求固定前缀提前装入所有插件，也不要为命中率隐藏可用工具；区分必要能力扩展与不必要 Schema 抖动。

### 4.5 压缩交接不得丢失事务

推荐一个压缩所有者，沿现有完整工具交换的边界处理。大工具正文先外置，再压缩旧交换，不把调用与其结果拆成孤儿。

交接材料分两部分：

**模型压缩的语义摘要**：最近讨论、已确认结论、尚不确定的信息、相关人物与原材料定位。

**宿主确定性附带的未完事项**：真实未处理来源、工作 ID 与 revision、原目标、等待有效性、累计预算／期限、已提交／已发送／未知的结果。

第二部分必须来自现有权威状态，不由摘要模型猜测；摘要不能创造或结束任务，也不能重置额度。原文仍按保留政策存在，精确引用必须回读。

正常重启时，恢复认知经历与恢复外部执行分开。旧记录没有完整轨迹，就从已知事件、摘要和真实事务建立新段并说明缺口；不能补造“模型以前看过”的历史。

### 4.6 多人并行与跨群个人记忆

群内先用一个主线，保留发言者、真实 reply、来源和工作归属。仅有名字或 ID 并不保证模型不串话题；也不需要立即使用模型为每条消息划分永久话题树。

跨群记忆暂不纳入第一版。以后确有需求时，在现有记忆记录中分别表达**描述谁**与**允许在哪里使用**。用户身份可关联，私有群原话仍限原群；只有被明确允许共享的个人偏好才跨场景使用。过滤在召回和 top-k 之前，不把全部内容交给模型后再要求保密。

## 5. 第二份核心合同：每次行为能还原到什么证据

### 5.1 将“完整可审计”分为三层承诺

**执行可追溯，是核心承诺。** 能连接真实输入、运行、调用、工具结果、提案、提交、行动和回执；沉默与失败也有真实阶段。

**请求可还原，是有保留条件的承诺。** 对实际留存的原文、工具结果、提示／工具版本和媒体引用，能还原其请求布局及提供范围；材料已清理、供应商转换不可见或历史缺档时，明确显示缺口。

**重新运行不在承诺中。** 读取日志中的链路不应再次调用模型、工具或平台；相同输入也不承诺相同输出，更不能据此宣称恢复模型的内部思考。

### 5.2 每次调用最小可追溯材料

| 项目 | 记录方式与边界 |
|---|---|
| 来源与关系 | 复用 event/episode/call/tool/job/revision/action/receipt ID，不猜时间邻近 |
| 上下文 | 记录最终裁剪与合法 hook 修改后真正提供的顺序、引用、范围、省略与媒体清单 |
| 提示和工具 | 记录可解析的版本；不能只写名称，因为同名内容可能改动 |
| 模型与传输 | 记录实际配置绑定、协议、可观测请求标识；供应商内部不可见部分不臆测 |
| 工具结果 | 已取得、已保存、实际提供的片段分别表达；目录和摘要不自动变成已读正文 |
| 决定与提案 | 保留可观察输出及模型实际给出的简短说明，不要求重建隐藏思考 |
| 提交和外部行为 | 保存事务、发布、入队和真实回执；未知保持未知 |
| 时间和用量 | 分阶段耗时、实际 usage、未知字段、估计、已配置报价与账单范围 |

不要永久复制完整群聊请求或 Base64，也不要把凭据写入 manifest。优先引用现有不可变记录，必要时保存小型版本化定义；无法据此逐字重建时，只承诺能够还原材料与阶段。是否提供一次授权的临时诊断导出，沿原鉴权与保留政策处理。[R05]

“内容实际提供给模型”只是可观察事实，不能升级成“模型理解正确”。`answer_basis` 证明关联到哪些材料，也不能单独证明结论无误。

### 5.3 不能被合并的状态

```text
模型生成 ≠ 提案通过
提案通过 ≠ 成功发布
成功发布 ≠ 平台收到
文件生成 ≠ 文件上传
搜索命中 ≠ 正文已提供
模型说取消 ≠ 远端执行已停止
缺失 usage ≠ 没有费用
```

本地事务使用现有幂等身份；外部平台没有相应保证时，不宣传全链路 exactly-once。未知结果不能直接自动重试，因为重试可能让别人收到两份消息或重复执行动作。

回退也不是删除新数据库回到过去：新期间已经发出的消息、已经执行的操作和已经发生的费用，必须继续保留与解释。[R02][R05]

### 5.4 把审计做成日常界面

运营者打开一句回复，先看到：关联谁、当前结局、主要来源、是否送达、花费和耗时。再展开详细调用与原始记录。

打开一个没有回复的来源，先看到：未观察、等待处理、主动沉默、缺补充、限额、失败、提交冲突，还是发送未知。没有记录就说没有记录，不让页面临时调用模型生成一个“当时原因”。

管理操作继续走原 Actor／配置锁和审计事件，不在路由新增任意 SQL、直接写状态或第二权限判断。

## 6. 第三份核心合同：第三方插件可以稳定依赖什么

### 6.1 保留现有公开入口，不重新发明 SDK

保留 `plugins/api.py`、`PluginSpec`、`BasePlugin`、`PluginCallContext` 及已存在的工具、事件、Agent 调用、工作和提交入口。描述符继续是元数据唯一来源；配置继续进入根配置与现有 Schema 表单。[R04]

新规划不是让第三方直接学 `Runtime`、`ProposalLedger` 和完整 `EventStore`。它应得到一次调用的明确上下文和必要服务，宿主承担身份、范围、预算和归属。

### 6.2 插件契约表

| 插件可稳定依赖 | 宿主的承诺 | 插件不应承担 |
|---|---|---|
| 描述符与版本 | 确定发现、重复 ID 报错、装载前明确兼容判断 | 维护第二元数据文件 |
| 调用上下文 | 当前场景、来源、真实发起者、角色、作用域和调用 ID | 从文本猜身份、创建假人类请求者 |
| 工具注册 | 参数模型同时定义 Schema 和解析；资格在执行前复核 | 自建工具循环或绕过准入 |
| `invoke_tool` / `run_agent` | 沿原计量、日志和当前范围运行 | 创建另一套 LLM 客户端和会话历史 |
| `emit_event` / 工作入口 | 保存真实来源，按资格唤起并形成持久工作 | 直接调用群聊主脑的私有函数 |
| `submit_message` 等提交入口 | 统一事务／发布／回执语义 | 直接调用平台接口并伪造“已发送” |
| 结果与资产 | 保存位置、读取范围、真实产物与交付分开 | 以本地文件路径当作平台已收到 |
| 生命周期 | 装载、配置变化、卸载和取消范围清晰 | 描述符导入时启动后台任务 |
| Hook | 顺序、可写字段和错误行为有明确合同 | 改写原话、授权、读取资格或回执 |
| 状态存储 | 配置和运行数据路径清楚；限定范围服务可用 | 长期实例保存可变“当前群” |

表中方法引用既有公共入口；建议新增的 `api_version` 只有被采纳并落地后才属于正式 API。本书不是新 SDK 的实现或已发布接口说明。

### 6.3 工具、确定性命令、事件与工作不要强行统一成一次模型调用

“现在几点”可以读工具后直接回复；“用自然方式告诉大家今天安排”可以调用 Agent；“开播了”是业务事件，Agent 决定要不要表达；“整理本周活动成文档”是持久工作。

四种入口共享调用与执行事实，但没有必要让每个简单命令都支付模型费用。插件可以拥有业务编排，不能拥有一套私下的群会话、权限、账本和发送系统。

### 6.4 Hook、停用和错误的具体语义

只读观察 Hook 不改业务输入；修改型 Hook 只允许改变声明的局部请求材料或工具子集，顺序固定，可追踪其修改结果。两者都不能创造用户来源、扩大权限或替换真实回执。

错误不静默吞掉后转入另一套默认聊天；取消是控制信号，不等同一般工具失败后继续模型循环。卸载取消本插件尚未提交的工作并按归属关闭资源；已经提交／已经发生／结局未知的事实继续保留。

插件始终按当前资格执行。低频发现、动态工具展开与缓存优化之间允许取舍，不能为了稳定工具表放开停用插件。

### 6.5 版本与信任边界

建议为公共 API 建立独立世代，插件自身采用版本号说明功能变化。早期不兼容可以明确拒绝并提供一次迁移，不用永久兼容补丁。稳定合同一旦发布，同一支持范围内不得无说明改变语义。

当前同进程 Python 插件按“运营者信任的代码”处理。缩小 API 有助于防止误用和降低耦合，但不是恶意代码沙箱。以后使用进程隔离主要解决故障和依赖隔离，仍不能自动等同强安全边界。

## 7. 群聊 Agent 的完整行为，应如何串起来

### 7.1 一条贯穿案例

某群成员请求“查下周活动，整理成文件”；Bot 接受工作后，群里继续聊天；另一成员向 Bot 发出普通问题；原请求者又补充“只留周末”。

理想路径不是每条消息各开一份工作，而是：原事件进入群主线；短查询在当前循环处理；文档任务保留自己的 job/revision；只有与该任务明确相关的修订改变其目标。工作完成后返回原场景，运行时核对最新版、原范围和可交付资产，再由群聊判断进行表达，最后真实回执决定是否交付。

过程中有五种连续性：群聊没有被长任务阻塞，原委托没有丢，补充改到了正确任务，普通问题没有串进该工作，文件生成与真正发送没有混为一谈。

这条普通场景比“再加一层自主 Agent”更能证明框架完整。

### 7.2 自然参与

真实 @ 或引用提高观察优先级，但不代表一定有回答义务；一句“哈哈”可以结束。被直接交流后保留有限关注，接住后续省略称呼的补充；到期或无可说内容就退出。

不让“等群聊安静”成为无限延迟：合并有边界，新的无关消息不持续重置等待。短写事务与网络／模型等待分开，保留已有 Actor 单写者机制。

不引入前置语义分类模型、不设置永久心情数值来替代语境，也不通过增加发言率证明自然。具体窗口数值来自真实配置与实际观察，本路线不擅自替换生产参数。

### 7.3 有限主动性

原 Scheduler／Heartbeat 负责触发；既有主体、范围、额度与睡眠规则负责是否入场。公共研究结果是候选，不自动广播到所有群；目标群在当前语境决定是否表达。

无有用主题可以不调用模型、没有值得分享的成果可以不发言。主动性应当让用户获得有用结果，而不是让日志一直有新任务。

### 7.4 低成本的目标函数

核心指标是“每次有效互动或完成工作的总成本、延迟与质量”，缓存率只负责解释输入费用的一部分。

统计至少分普通对话首请求、轮内工具续调、长期工作、压缩／历史维护；命中率按有实际字段的 token 加权，并显示数据覆盖率。实际计费、估计价格和未知报价分开，代理渠道的计费不由上游缓存字段推断。

不承诺具体供应商 TTL 或并发缓存数量；没有新活动时不为保温发送请求。250K 是可选容量参数，不是必须填满的目标。对同样任务有用的短上下文可能比高命中但过长的上下文便宜；采用何种容量应以真实结果为依据。[R12]

## 8. 分工、依赖与推进节奏

### 8.1 五种负责人角色，不假设已有五个人

| 角色 | 责任 |
|---|---|
| P：产品与维护负责人 | 范围、架构决策、兼容承诺、是否发布；最终取舍由维护者负责 |
| K：内核与数据实现 | 场景、上下文、工作、执行、计量与持久化 |
| E：插件与业务集成 | 公共 API、生命周期、参考插件、内置插件适配 |
| U：界面与使用文档 | 现有前端、操作路径、新手与开发者文档 |
| R：发布、复核与验收记录 | 同版证据、支持矩阵、构建、升级和已知限制 |

单人项目可以由同一个人在不同阶段承担这些角色。每项任务只有一个负责交付的人，协作者和复核者另行注明，不用虚构多人审批组织。

### 8.2 依赖图

```text
S0 产品合同与基线
 ├─ S1 可追溯执行 ─┬─ S2 会话连续性 ─┐
 │                 └─ S3 插件合同 ──┤
 │                                  ▼
 │                            S4 群聊体验集成
 └─ S5 安装/文档提前整理 ────────────┤
                                    ▼
                              S5 产品收口
                                    ▼
                              S6 候选与发布
                                    ▼
                              S7 独立使用与 1.0
```

S2/S3 只有非冲突任务可并行；公共结构未定时不让多个实现者分别修改。建议同时只有一个共享内核变更和一个不冲突的文档／界面工作在进行。正常缺陷修复不必等待整条路线完成。

每次交付一个从输入到可见结果的完整小路径，不先把所有抽象做完，再尝试拼接。八个阶段是达成条件，不是日期或工期承诺。

公共 API 的稳定不是“每个内部类型都导出”。常见插件只需声明业务、读限定资料、调用工具／Agent、创建工作和提交表达。

三个参考场景优先利用已有 local_clock、日历／开播和工作插件。示例与 Schema 的矛盾必须在同一个 PR 修正；不要再写一套类似而行为不同的“新示例宿主”。

**阶段验收门槛：**一个目录、公开入口和清楚版本即可完成读取、事件唤起或后台工作；停用、错误、取消与审计有一致语义。

## 9. 如何管理开源项目，而不制造一套管理负担

### 9.1 一份路线索引、一组任务状态

代码库中的当前行为由所属文档说明，未来目标只维护一份路线索引，实际进展和缺口写入 `iteration.md` 或其既有后续机制。任务进入 Issue 后，路线只引用 Issue 和里程碑，不重复维护完整进度。

任务状态可保持简单：待确认 → 可实施 → 实施中 → 待复核 → 已验收 → 已发布；阻塞原因作为字段，别再发明一套与运行时业务状态同名的枚举。

标签优先类型和模块，例如缺陷／功能／文档、上下文／插件／运行／界面，另标破坏变更和待证据。没有必要将 48 项任务全部分裂成数百标签。

### 9.2 一个 PR 应当包含什么

一项用户结果对应一个主要 PR，包含代码、所属合同、受影响样例、界面术语及兼容说明。目录重排和功能新增分开，不用大面积格式化淹没业务修改。

PR 正文至少说明：本次真实问题，修改路径，不改变的边界，新增状态／字段的必要性，实际验证方式与结果，未确认部分，升级／停用／回退影响。

核心状态所有权、公共 API、数据结构改变应先有一个短设计决策；普通局部修复不要被迫写长 RFC。当前单人阶段由维护者决定合并，不要求两位不存在的 reviewer；有外部贡献者后再逐步分配领域复核。

### 9.3 分支和发布

保留当前主分支名称。日常用短 `feat/…`、`fix/…`、`docs/…` 分支；需要候选稳定期时临时开 `release/…`，只收阻塞修复与发布材料。

发布标签必须对应实际复核的提交与产物；不要给一个旧提交的实测报告搭配另一个新提交的镜像。版本说明分别写用户可见变化、插件 API 变化、数据／配置迁移、支持组合及已知限制。

预览版可以提前发布限定范围的成果：S1/S2 后的内核预览、S3 后的插件开发预览、S5 后的可安装候选；这些是建议节点，不代表必须等到 S7 才允许别人体验。

### 9.4 支持和贡献规范

问题报告要有版本、环境、实际渠道、预期／实际、必要的脱敏日志和来源 ID。安全问题提供私下渠道，不要求用户把密钥和整个群历史贴到公开 Issue。

小众业务优先插件；跨所有插件有意义的机制才进入核心。新的外部贡献需要基本授权声明和明确许可，不必一开始就引入复杂 CLA、委员会或企业 SLA。

代码作者身份、人类贡献和历史提交按真实情况维护。本路线不添加工具共同作者，不改写 Git 历史，不代替用户提交或发布。

### 9.5 完成的统一定义

“代码写完”不等于“实现完成”；“实现完成”不等于“该组合已支持”；“已支持”也不等于“生产已经部署”。

一项任务关闭前，应明确：用户结果是否达成，所需数据是否可追溯，样例／文档是否同步，当前验证证据是什么，未确认范围是什么，以及能否安全停止新增入场。实现未变但已有同版证据足够的任务，可以直接以证据关闭，不要求为了完成任务再改代码。

## 10. 验收材料：复用已有 A01—A30，不造第二套测试系统

### 10.1 观察记录模板

```text
任务 / 目标：
候选 commit / 构建标识：
配置修订 / 已启用能力：
模型、提供商或渠道 / 平台适配器版本：
实际获准的操作与执行者：
来源 event_id / episode_id：
call_id / tool_call_id：
job_id / revision：
action_id / receipt：
观察到的结果：
是否已提交、是否真实送达：
费用是实际报告、估算还是未知：
未覆盖或仍未确认的分支：
相关缺陷 / 文档变更：
```

只记录必要信息，脱敏后用于支持；密钥、无关个人信息和全部群原文不进入公开记录。

### 10.2 关键业务观察与证据

| 观察场景 | 应看见什么 | 可接受证据 | 没有现场证据时 |
|---|---|---|---|
| @ 后跟进、对回复感叹、自然结束 | 能关注补充也能沉默 | 原事件、观察状态、运行结局 | 只说设计已接入，不说接话体验已好 |
| 同群多人交错交流 | 请求归属与来源覆盖不混 | 实际 reply、speaker、source、提案关系 | 不用单用户示例证明多人正确 |
| 短查询／计算 | 原循环取得必要资料并回答 | 工具结果实际提供范围、提交与送达 | 搜索命中不算已查证 |
| 长工作与目标补充 | job/revision 继承，群主线继续 | 工作记录、事件、预算和最新结果 | 不通过人为压力证明不阻塞 |
| 正常取消／修订／恢复 | 原预算与期限保留，旧结果不被当新成功 | 真实正常控制流程和回执 | 特殊竞态只登记源码核对 |
| 正常跨越上下文阶段 | 未完事项、近期语境和引用仍可找回 | 新旧段关系、摘要、原状态、材料范围 | 不刻意灌大量无效消息制造边界 |
| 纠正与后续取用 | 当句改正，之后不采用失效认识 | 原纠正、supersede/refute、检索范围 | 没有后续真实取用就暂不声称持久生效 |
| 文件交付 | 生成、登记、可下载、实际上传分别显示 | 原资产、action 与平台文件回执 | 本地文件或路径不是已上传 |
| 已出现的发送失败或未知 | 不说成功，不自动重复 | 既有实际失败记录及处理路径 | 不为验收造断网或未知回执 |
| 外部插件停用和正常升级 | 当前资格即时生效，资源有归属 | 生命周期记录、调用和配置版本 | 不以描述符能导入替代完整运行 |
| 正常安装与升级 | 文档、配置、数据、产物同版 | 独立操作者的实际步骤与结果 | 作者本机成功不当所有环境成功 |

当前 A01—A30 可映射到上述目标，而不是重新造一批自动回放样例。其他人的群资料和生产操作必须有相应授权；没有授权就保留未确认。[R05]

### 10.3 采用哪些指标

**用户结果**：明确请求是否被正确处理、是否出现不必要打扰、纠正是否被采用、工作是否按修改后目标交付。先保留具体反例，不急着汇成一个真假分数。

**执行正确性**：已知来源到行动的关联覆盖，是否存在虚假完成、重复交付、工作归属错误或未知被抹掉。没有观测到问题不等于证明问题不存在。

**运行效率**：有效交互／工作总费用、模型及工具调用次数、首次有效回应延迟、等待和装配开销。样本太少不报告稳定的 P95/P99；若统计分位数，必须附样本数、窗口和口径。

**上下文**：首请求和续调缓存分别统计，压缩调用成本，真正进入模型的范围，重复检索和失效认识使用情况。不同模型、任务、渠道不能混成一个收益数字。

**产品成熟度**：独立安装是否成功、外部作者是否能只用公共 API、升级是否需要作者代劳、常见问题是否能靠文档定位。这些比代码行数、Star 和插件数量更接近当前目标。

## 11. 1.0 的发布门槛

1. **独立使用。** 至少已有非作者使用者在明确支持环境内按文档完成安装、日常业务与正常升级；角色预设不是通用运行的障碍。
2. **连续性明确。** 普通群聊、会话段、工作和长期记忆的生命周期有一致实现；压缩／恢复不会靠摘要猜任务状态。
3. **事务真实。** 已提交、已执行、已送达和未知有区分；没有已知的核心虚假成功、跨场景归属或重复副作用阻塞项。
4. **插件合同可依赖。** API 版本、常用入口、生命周期、结果和错误语义稳定；至少一个真实外部作者闭环成立。
5. **审计边界诚实。** 能追溯公开承诺的主链；缺材料明确；没有宣称完整模型思考、不可见上游调用或未保存内容能全部重建。
6. **可维护发行。** 标签、构建、文档、支持矩阵、升级／回退说明和该版人工证据一致；有持续处理问题的方法。

这些是建议采纳的发布合同，不是本次已验证结果。任何明确的核心阻塞项未闭合就保持预览或早期版；个别可选业务未开启不阻塞核心发布。

若持续无法在少量核心链路上稳定收口，首先缩小稳定范围，不再添加第三套记忆、调度、审计或 Harness 来掩盖基础问题。

## 12. 后置能力：有真实需要再进入路线

| 能力 | 启动条件 | 最小边界 | 不应作为首版门槛的原因 |
|---|---|---|---|
| 第二消息平台 | 已有独立使用者确实需要，并能确认平台语义 | adapter 负责协议，宿主提供规范化主体与场景；明确消息／文件能力矩阵 | 抽象尚未稳定时多平台会放大身份和回执问题 |
| 跨群个人记忆 | 本人选择共享且确有跨群使用场景 | 现有知识账本增加明确范围，过滤与派生上下文失效一致 | 关联身份不等于可以跨群传播私事 |
| Hermes 等外部执行器 | 某类工作维护成本可被明确降低 | 仅接 job 执行段，返回进度／资料／结果／取消结局；LenBot 保留群状态和发送 | 全面接入易形成两个会话、调度和压缩所有者 |
| 独立进程插件 | 依赖冲突或故障隔离有实际证据 | 先保留 SDK 语义，明确进程退出和在途调用；安全边界另核对 | 进程隔离不自动解决权限、版本和审计 |
| 插件目录／市场 | 已有多个独立维护插件，人工链接难以管理 | 先做可审阅的静态目录和模板 | 不应先建市场服务再等待插件生态 |
| 更强自动验证 | 维护者明确修改当前工程约束 | 从既有关键路径、真实回归和现有设施开始 | 当前禁止，不能通过探针／回放名义绕过 |

不将“自己完整开源”理解为必须重写一切底层组件；也不因一个外部项目更有名就交出全部状态所有权。依赖应降低复杂度，不该产生两套互相补洞的系统。

## 14. 第一批实际应分配什么

第一批不要同时启动 48 项任务。先完成 **S0-01、S0-02、S0-05、S0-06**，确认当前基线、三个合同和唯一剩余清单；许可证与素材说明 **S0-04** 同步处理。

随后用 **S1-01、S1-02、S1-06** 打通一条现有普通回复的只读解释路径。若现有字段已足够，则主要是查询和页面收口，不强行改运行时。

在这一条路径能解释输入、调用与真实结果后，再进入 **S2-01** 的会话段设计和 **S3-01** 的公开 API 版本决策。先决定所有权，再分配实现，避免多个实施者围绕同一概念各建一套状态。

每个新想法都问：它补了哪个已承诺的用户结果？应进入内核、插件还是预设？有无现有入口可复用？怎样证明完成？答不清就先留在想法区，不扩大当批范围。

**成熟的标志不是 LenBot 又能做一件新鲜事，而是同一件事在离开作者亲自照看之后，仍然能被别人理解、使用、扩展和维护。**
