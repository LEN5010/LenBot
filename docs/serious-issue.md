# 待决问题：对话缓存命中

记录一个尚未定案的问题，以及为它做过的测量、被否定的假设和已知的方法缺陷。本文不是结论，是给下一轮排查的交接。行为边界见[当前架构](architecture.md)，每轮请求怎么拼见[上下文装配](context.md)，本轮实测见[当前任务](iteration.md)。

此前「代码侧没有问题」「已排除时间与容量因素」的定案过度。工具定义是消息目录之外的请求变化来源，有限对照不能排除所有负载下的上游行为；本轮真实调用与历史分组复核只记在[当前任务](iteration.md)。

## 一、问题

对话调用的缓存命中率低于预期。2026-09-19 末两小时的真实流量：33 次调用、29 个轮次、5 个群，全部 `gemini-3.8-flash-high`。首次调用口径命中 54.28%，全部调用口径 59.57%。

峰值请求 175k 量级，缓存复用可能影响上游计费与延迟；网关扣额是否有折扣还取决于实际缓存倍率，不能仅凭命中比例推算运行成本。

## 二、已确认：锚定修复成立，但不代表整个请求稳定

两条都有实测支撑，可以销掉[上下文装配](context.md)§8「锯齿的全部收益都是推算」中关于锚定的部分。

**锚定机制全部生效。** `anchor_window_start` 在 29 个轮次中 **29/29 触发**，5 个群无一被挡、无一未触发。这是 `conversation_history_limit` 400→1500 之后第一次取得的数据，该修复成立。

**窗口头稳定。** 逐轮追踪窗口第一条消息的引用编号：

| 群 | 窗口头 | 连续保持 | 窗口条数 |
|---|---|---:|---|
| 1042218062 | `M34081` | 7 轮 | 773 → 794 |
| 126300994 | `M37000` | 5 轮 | 661 → 671 |
| 1090284567 | `M38005` | 5 轮 | 274 → 286 |
| 1102823315 | `M30027`→`M31149` | 5 轮后跨边界 | 901 → 908，跌至 876 |

`1102823315` 那次 `908 → 876` 是[上下文装配](context.md)§3 描述的锯齿本体第一次被真实观测到。

## 三、统计口径：字段缺失须结合中转转换行为解释

**缺失不是原始上游的显式零值，但没有显式零值也不能反过来否定未命中。**

复核 `model_calls.usage_json` 的实际内容：

| 形态 | 次数 |
|---|---:|
| `prompt_tokens_details` 字段整个缺失 | **11** |
| 显式 `cached_tokens == 0` | **0** |
| 正数 `cached_tokens` | 22 |

即最终保存的兼容响应中**没有显式零值**。11 次记录都未包含该字段，但这不能证明原始上游同样没有返回该字段。

当前中转转换只在 `cachedContentTokenCount > 0` 时输出 `cached_tokens`。所以上游返回零和没有上报都可能表现为字段缺失；仅凭最终响应不能区分二者，也不能因为没有显式零值而宣布整组数据无效。

本页的比例应理解为「已报告缓存 token 占输入 token 的比例」。涉及实际未命中的定案需要原始上游 usage 或受控请求变化的对照；第四节的有限观察同样不能推广成全面排除结论。

另一处相关缺陷：`context_plan.request.messages` 只保存 `role` / `ref` / `text_range` 等目录信息，不保存请求正文。**用目录相同来证明 token 前缀相同是不成立的**，本轮「前缀 93–98% 一致」的说法只到目录层面。

## 四、历史小规模对照的适用范围

从 `lmc`（出口 117.72.8.73，与运行主机不同）对中转发起真实请求。所有测试用合成语料，未使用任何群聊内容。

### 4.1 同一前缀并发：该组调用全部命中

同一份 30k token 前缀，6 路并发：

```
conc-0 ~ conc-5   prompt=30006  cached=24546  hit=81.8%   (6/6)
```

6 路全部命中，无一例外。

### 4.2 插入竞争前缀：该组负载未观测到驱逐

建立前缀 A（40k token），中间插入 4 份互不相同的 40k 陌生前缀，再回到 A：

| 步骤 | 命中 |
|---|---:|
| A 建立 | 0%（首次） |
| A 立即重复 | 92.1% |
| 夹入 B / C / D / E（各 40k） | — |
| **A 再次** | **92.1%** |

A 在被 4 份同量级前缀冲刷后**完整存活**。

> 注意：B、C 两笔也报 92.1%，因为它们与 A 共享很长的公共尾部，命中的部分可能是 A 的缓存而非自己的。这不影响对 A 的结论，但说明该测试的前缀区分度不够，后续应换用完全独立的语料。

### 4.3 TTL 到期：此前没有依据排除

此前把 60 分钟当作上游计费缓存的确定保留时间，但没有取得本链路的依据。转发器本地推理回放缓存的保留时间，不等于上游提示缓存的保留时间；短间隔重复调用也不能验证数分钟后的留存。时间因素须单独观察。

**结论范围：这些请求确实可以命中缓存。** 既不能凭 n=33 的相关性断言「多群共抢缓存池」，也不能凭较小负载的存活宣布已经排除容量、时间或业务请求变化。

## 五、新发现：缓存有最小尺寸门槛

同一份稳定前缀，只改长度，其余条件不变：

| 前缀字符 | prompt_tokens | 命中 |
|---:|---:|---:|
| 10,000 | 6,009 | **0%（10/10 次全 0）** |
| 50,000 | 30,004 | 81.8%（首次除外，5/5 稳定） |
| 66,000 | 40,005 | 92.1% |

6k token 一次都没命中过，30k 起稳定命中，门槛在两者之间，具体位置未测。

两点推论，都还需要复核：

1. **小群可能整体落在门槛以下。** `group:1090284567` 平均输入约 62k，是 5 个群里最小的，命中率也最低（48.6%）。但 62k 已远超 30k，所以这条不能直接套用，需要单独验证。
2. **前缀越大命中率越高**（81.8% → 92.1%），因为未缓存的尾部是相对固定的开销。

## 六、cline 备选链路当前不可用

`cline-pass/deepseek-v4.1-flash`（new-api 通道 6 → switcher 3123 → `api.cline.bot`）：

- 从 `lmc` 连发 **30 次并发请求，100% 全部 502**（`empty response content` / `upstream_error`）
- 零星手测时可偶尔成功（5 次中 2 次、4 次中 2 次），成功时命中 97.6%
- switcher 配置 `accountMode: single`，仅 1 个账号；每请求不打日志

即**间歇性故障，并发下必挂**。`lmc` 出口与运行主机不同，排除了本机网络被阻断这一解释。

另据[当前任务](iteration.md)同日的独立复核，该通道以短提示调用两次均正常返回，故**不能宣布整条链路永久不可用**；502 的具体成因未复现。

结论：该链路现阶段不能作为对照组使用。

## 七、仍然未解释的部分

去掉第三节指出的错误前提后，真正确定的只剩：

- 22 次调用有正数命中，形态为 83–89%
- 11 次调用上游未返回缓存字段，原因不明
- 其中 5 次是重启后每群首次调用，但本机重启本身不能证明上游缓存被清空
- 1 次是窗口头跨边界（锯齿自身代价，合理）
- **剩余 5 次需要按工具定义和时间间隔分开复核**，不能整体归因于容量

对这 5 次，不能再沿用「已排除并发、驱逐、TTL 与应用侧变化」的说法。应分开核对工具集合及完整 Schema、时间间隔与窗口边界；历史请求正文未保存，目录相同不能补足这一证据缺口。后续真实调用结论见[当前任务](iteration.md)。
