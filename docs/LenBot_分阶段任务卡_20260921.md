**本文件是路线书中同一套 48 项任务的分配视图，不是另一份独立总计划。所有任务目前均为规划；实际实施前重读 HEAD、iteration 和所属模块。已存在且同版证据充分的能力可以登记保留，不为了关闭任务再改一次代码。**

任务分工采用角色：P 产品／维护、K 内核／数据、E 插件／集成、U 界面／文档、R 发布／复核。同一个人可以承担多个角色；每次分配将负责人替换为真实人员，不虚构团队。

当前工程约束继续有效：不修改仓库、不运行生产或模型、不新增／修改／运行测试、夹具、回放、探针、故障注入和压力任务；后续实施只能使用获准的阅读、编译构建和正常人工操作。真实配置、主体、权限、群名单、人格原文不因本计划获得变更授权。

每一任务都需先确认现有代码是否已满足目标，再选择“保留并补证据”“定向修改”或“延期”。新增层、状态和表必须解释现有结构为何不足。

**阶段结束条件：**普通回复、确定性插件和一个工作交付能沿已有身份追踪；缺失、失败、沉默和未知彼此可辨。

**明确不做**  
不以版本号、缓存率或代码行数决定成熟度，不许诺尚未验证的可靠性。

**关闭任务时填写**  
实施 commit；实际修改符号；所属文档；实际编译／构建结果；获准人工记录及 event/call/job/action/receipt；未确认范围；升级影响。没有运行证据的项不得写成实测通过。

## S7｜用独立使用者证明框架成立

**目标：**把“作者自己能用”变成别人能够使用、扩展、升级与维护的公共产品。

**前置：**S6 有范围明确的公开候选／早期版本；社区模板可在 S0 即准备。

**阶段结束条件：**独立部署和插件开发闭环成立，支持负担可承受，发布承诺有持续维护办法，再决定是否标为 1.0。

### S7-01｜招募少量独立使用者

**建议负责人：**P（产品与维护负责人）。  
**涉及现有模块：**默认发行版、安装／支持文档。  
**依赖：**S6-06。

**具体工作**  
建议目标为 2—3 个不同群用途的自愿使用者，包括至少一个非 A-SOUL 场景；由对方照文档操作，记录卡点而不是作者代装后宣称开箱可用。

**交付物**  
独立安装反馈和真实文档修复。

**验收与证据**  
他人完成接入、日常使用与一次升级；收集内容有授权，群消息不公开泄露。

**明确不做**  
不承诺用户数量、不提前做推广规模化、不用维护者代操作充数。

**关闭任务时填写**

### S7-02｜完成一次外部插件作者闭环

**具体工作**  
让至少一名外部作者按公开示例开发其真实需求；记录必须咨询内部实现或改核心的地方；优先补公共合同缺口而非为单插件加特例。

**交付物**  
外部插件案例与 SDK 改进记录。

**验收与证据**  
作者可完成注册、配置、调用、停止与排错；不依赖私有 Runtime；独立业务不迫使内核变成该业务。

**明确不做**  
不以维护者自己改了个模板替代外部可用性，也不急建在线插件市场。

**关闭任务时填写**  
实施 commit；实际修改符号；所属文档；实际编译／构建结果；获准人工记录及 event/call/job/action/receipt；未确认范围；升级影响。没有运行证据的项不得写成实测通过。

## 可直接复用的任务 / Issue 模板

```markdown
## 对应路线任务
Sx-xx；所属现有模块 Mxx；实际基线 commit。

## 用户结果与实际缺口
谁在什么场景遇到什么问题？当前实现在哪里断开？
已有能力是什么？为什么不是重复实现？

## 范围
允许修改的模块／文件／公共符号。
必须保留的身份、事务、预算、范围、回执和配置边界。

## 实施方式
最短路径；必要的数据或 API 变化。
新增抽象、表或状态分别解决什么具体缺口？

## 完成条件
必须能观察的结果。
哪些只能做源码核对，哪些已有正常人工记录？

## 依赖与决策
依赖任务；待维护者确认的产品／兼容决定。

## 交付证据
实现 commit、文档、构建、获准人工观察及对应身份。
失败原文、已提交／未提交、是否真实发送、未知内容。

## 非目标
不改的模块、参数、人格、权限、生产环境和旧历史。

## 升级／回退
旧配置、数据、插件和在途工作如何处理？
哪些外部行动无法通过代码回退撤销？
```

## 任务使用顺序

先分配 S0 的核心决策和基线；再完成 S1 一条可追踪路径。S2/S3 只并行无冲突工作；S5 文档可提前整理。未达成阶段门槛时，不以新增功能掩盖该阶段缺口。

源事实、模块定义、设计理由与资料链接见主路线书第 15 节。任务中的推荐字段和目标行为都是待采纳设计，不将其当作当前代码已有能力。
