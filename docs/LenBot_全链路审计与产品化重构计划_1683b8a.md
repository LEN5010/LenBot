# 2. 已确认的问题：先修这些，不重开已经正确的旧修复

优先级按影响定义：P0 是放行前必须修复的安全／交付合同；P1 是正常使用阻断或明显正确性问题；P2 是有明确代码依据的体验或边界问题。低优先级不表示可以用文档声明代替修复。下述场景均是源码推导，除另说明外未在本次实际运行。

## A01｜P1｜无群专属参数的插件，不能从本群界面新增

**源码位置：** `web/frontend/src/components/SceneSettingsForm.vue::readyToAdd/addPlugin`；`plugins/catalog.py::PluginSpec`；`plugins/models.py::EmptySceneConfig`；`web/query_service.py::scene_settings`。[S13][S14]

`readyToAdd` 同时要求全局已配置和群 schema 有至少一个 property。但插件默认采用 `EmptySceneConfig`，合法群参数就是 `{}`。接口把这些插件也列给页面，页面却将其“添加本群设置”按钮禁用，并显示需要先填全局参数。

**触发：** 全局已经配置的无群参数插件，尚未出现在一个新群的 `settings.plugins` 中。已有配置条目不受这个“新增”按钮问题影响。

**改法：** 分开三件事：能否建立群级启用记录、是否需要填写额外参数、当前实际是否可运行。空 schema 表示没有额外参数，不是未就绪；新增时写入 `enabled:false, config:{}`，由用户明确启用。全局未启用／有运行错误另外显示，不能用 schema 大小推导能力可用性。

**不接受：** 为所有空配置插件伪造一个无用字段；要求用户离线改 JSON 绕过正常界面；悄悄给所有群批量启用。

**完成条件：** 新群能添加一个空群参数插件和一个有必填群参数插件，前者无需造参数，后者缺值有字段错误；仅添加不产生模型调用、网络执行或群发送。

## A02｜P1｜自然的认识修订竞争仍可能阻断后续整群历史维护

**源码位置：** `runtime/agent_runtime.py::_maintain_history`；`scenes/actor.py::_commit_history`；`memory/history.py::begin_history_batch`。[S15][S16]

本轮已正确修复 `committed_memories, _` 的解包问题，并区分提交前／提交后失败。不能再把旧日志的解包异常列为未修。

剩余时序是：维护捕获全局知识版本 r → 调用模型 → 对话开始并把认识改成 r+1 → 维护让出活动对话 → 仍用 r 提交 → Actor 拒绝 → 批次被标 failed。`begin_history_batch` 对同群任意非 completed 批次直接返回 None，所以后面原话虽然继续保存，摘要维护会一直停到人工处理。

**问题本质：** 全群知识版本把“不可变原话摘要的维护”与“任意一条认识修改”绑得过紧；安全拒绝是合理的，但把正常竞争转成整群长期停止，不是理想运行策略。

**短期改法：** 将这种竞争明确显示为过期候选／待核对，不再与供应商失败混为一类；保留原始范围、候选、模型消费和版本。对没有认识修改的纯摘要，按真实来源范围和覆盖约束提交，不因无关认识变化失败。

**目标收口：** 对认识变更采用具体目标记录的版本和证据检查；涉及过时语义的候选不可直接换成当前版本号提交。需要重新判断时沿原维护预算进行明确的候选重核，不购买无穷新循环。若实施中必须将“摘要覆盖提交”和“认识变更提交”拆分，先写明这是原子合同变更，保证未采用的认识候选不会因摘要进度推进被遗忘；使用已有批次、提案和 Trace，说明新增持久字段的用途，不另建记忆平台。

**完成条件：** 维护生成期间一名群友纠正称呼，最终不会覆盖纠正，不会报已提交为未提交，也不会让之后一整天的历史维护静默停止。

## A03｜P1｜本机 worker 没有落实 Gateway 已有的锁后修订核对

**源码位置：** `execution/service.py::WorkspaceService.scope_for/run_python`；`browser_agent/plugin_core.py::_scope`；对照 `browser/gateway_service.py::_job/execute`。[S17][S18]

本机 Python 在进入运行锁之前读取归属和状态，取得锁之后导入数据并运行脚本，没有核对调用携带的 `job_revision` 是否仍为当前版本。允许的状态还包含 `result_ready`。本机浏览器 `_scope` 同样未校验 `call.job_revision`。

**触发：** 原调用等待执行锁／其他 await 时，用户修订或取消工作；旧调用到达真正执行点时，缺少独立的当前修订检查。外层的取消传播会减少机会，但不能代替实际副作用入口的版本合同。

**影响限定：** 这是旧调用有机会越过新版本边界，不是已证实越权执行事故。仓库最新记录恰好使用本机 worker，因此不能只验证 Gateway 然后宣布该路径通过。

**改法：** 把工作主体、插件资格、修订、可执行状态、原 deadline 的准入收敛到现有宿主服务的同一函数；各执行驱动在锁后和真正发出操作前使用它。调用携带原修订，不从最新工作偷换身份。前端明确本机试用与正式 Gateway 的差别。

**完成条件：** 原调用在等待中遭修订，不能以新修订身份运行旧脚本；当前版本的正常调用不受无关修改影响；取消后只有清理与已有回执保存可以继续。

## A04｜P1｜本机输入清单不等于真实挂载内容

**源码位置：** `execution/service.py::WorkspaceService._export_inputs`；`execution/workspace.py::_run_python_locked`。[S17][S19]

本机导入在同一个 control/input 目录增写本次文件并替换 manifest，没有移除上一请求的输入；容器继续只读挂载整个 control 目录。

**触发：** A 次导入图片／文字，B 次只选择新输入或不选择任何附件。B 的 manifest 只描述 B，容器仍可以读取 A 留下的输入。

这属于同工作内的输入新鲜度与来源合同错误，不据此认定跨工作泄露。持续可写 workspace 中保留用户自己生成的文件，是另一个明确设计，不应与“本次导入集合”混淆。

**改法：** 每次执行建立独立输入快照：先完整准备到临时目录，成功后固定本次只读输入路径，再启动。仅收尾本次临时输入；不删除既有成果或跨执行明确保留的工作文件。失败前不让部分输入变成正常 manifest。

**完成条件：** A 导入的附件不会在 B 的本次输入挂载中偷偷出现；manifest 中每一项都存在且完整；导入失败不运行脚本。

## A05｜P0（延期交付放行前）｜重启防重补了，但同一事项的后续消息依赖未持久化

**源码位置：** `actions/queue.py::_request_failed/_remember_failure/_process`；`actions/delivery_store.py::recover_deferred_delivery_tasks/claim_deferred_delivery`；`runtime/agent_runtime.py::_release_deferred`。[S08]

本轮已在真正发送前保存 `DELIVERY_ATTEMPTED`，并把无回执尝试视为 unknown，这解决了上一轮重要的重复发送窗口，应保留。

但“前一条未确认送达，停止同一请求后续消息”的依赖只在 `_failed_requests` 内存字典里。延期任务恢复逐条看自己的 action_id，没有检查同一事项的前序行动。`_process` 见到任意既有 delivery_fact 直接返回 True，也没有区分它是否是失败或 unknown，不能借此恢复失败依赖。

**触发：** 同一请求的 A、B 两条消息都延期；A 发送结果 unknown，B 仍未尝试；在 B 处理前重启。A 不会重发，但 B 可能被当成独立可发消息继续发送，与队列声明的依赖规则不一致。

**改法：** 不新增第二条消息队列。基于已有 batch_id、batch_index、原事项关联与持久发送事实，恢复必要的依赖判断；只有真实依赖的消息受限，不能阻塞同群无关请求。不同动作类型不能通过“已存在任意记录”一律视为成功。

**完成条件：** A 未知时 B 不继续依赖性表达；A 成功时 B 可以继续；同群无关的即时日历卡片不被阻塞；unknown 不重发；原任务和延期任务都能沿真实回执终结。

## A06｜P2｜只改白名单，也可能悄悄改变其他授予的到期时刻

**源码位置：** `SettingsView.vue::toLocalInput/saveAccess`；`web/routes/settings.py::_grant_content/update_access_settings`。[S20]

到期 epoch 回填到 datetime-local 时只保留分钟；保存整页时对每条授予重新解析输入框。原值带秒或更高精度时，哪怕用户只改白名单，也会截到该分钟起点。后端比较完整内容，可能将其认定为修改授予，递增修订并改变签发者。

**改法：** 未修改到期字段时原值原样传递；修改时显式选择支持的精度，日期控件、校验与展示一致。白名单和授予允许独立提交，服务端只改明确提供的字段；现有事务与授权保持。不把改动原值重置为另一个“原始值”来掩盖 dirty。

**完成条件：** 例如原截止 18:00:37，仅改白名单后仍为 18:00:37，同一条未改授予的修订及签发者不变。新增、改期、撤销分别通过。

## A07｜P2｜debounce_max_ms 不是实际硬上限

**源码位置：** `events/builder.py::BurstAssembler.ingest/_wait_and_flush`。[S02]

代码只在新事件到来时检查缓冲年龄；未达到最大值时仍设完整 idle 定时器。因此最后一条消息在 max 前到达、之后安静时，真正 flush 可以迟至接近 max+idle。

**改法：** 每次计划 flush 使用 `min(idle_deadline, first_arrival + max_deadline)`，用同一单调时钟表示本地间隔。@/真实回复的即时处理保留；明确称呼是否使用短合并窗口是产品策略，不冒充既有 bug。

**完成条件：** 连续消息、最后一条恰在 cap 前、无新消息三个情形都遵守真正最大本地等待时间；不因修计时而重复生成 burst。

- 系统心跳不再被群级 enabled 提前拦截；已有真实工作创建，不再固定写空结果。
- 审查不再仅用 job:type 复用；已有不可变 ActionRequest 与真实模型调用。
- Gateway 浏览器不是单纯的“永久拒绝占位”；已有服务与有身份命令链。
- 延期交付有稳定 ID、原定时间、叫醒重评估和发送前持久记录。

以上仅表明对应旧缺口出现了修复代码，不能替代本轮完整链的运行验收。[S07][S08][S09][S10][S11][S20]

# 3. 关于群聊：为什么会不灵敏，以及上午的沉默到底去哪了

## 3.1 不要把“没回复”都称为注意力差

目前至少有六种不同情况，界面却难以让普通运营者一眼分清：

1. 消息存入了，但没有称呼／关系／关键词／抽样机会，未启动模型。
2. 有机会，正在等 burst、全局模型名额或本群上一轮。
3. 模型运行了，但当前输入窗口没装进关键原话。
4. 模型实际读到并合理选择沉默。
5. 模型输出了，但参数、预算或 Gate 冲突导致未提交。
6. 提交了，但睡眠、发送资格、传输或未知回执阻止交付。

必须分别观察再调节。将概率调到 1 只能影响第一层，修不了后面五层，也可能显著增加模型消费。[S02][S03][S07]

## 3.2 当前注意力的真实上限

入口在模型之前依靠称呼、@、回复、活跃参与者、在途互动、受托工作、等待关系，再补关键词和窗口抽样。普通话题内容的含义并不是在每条消息上由语义模型判断。抽样是每时间窗口一次机会，不是每条消息一次概率。[S02]

在“每个窗口均有符合抽样条件的普通消息”等假设下，窗口 W、命中概率 p 的平均机会间隔约 W/p；这是数学说明，不是对用户真实配置和延迟的测量。不要拿样例文件的 W/p 当生产参数。

之后还存在全局 semaphore、本群串行会话、上下文装配、附件读取、模型请求、工具、提交和发送等待。当前新输入主要在模型交换边界吸收；已有长对话或昂贵图片操作可能令人感觉没及时接话。[S03][S04][S07]

## 3.3 晨间原话的四层状态

| 层 | 当前能力 | 限制 |
|---|---|---|
| 原话账本 | 普通可见消息可保存，与 Bot 是否发言不是同一决定 | 插件消费／排除、作用域和保存边界必须单独看；不是所有系统材料都算聊天原话 |
| 近期工作记忆 | 初始窗口选近期 raw、当前请求邻居、相关工作原请求 | 受条数、token、优先级限制；不自动覆盖一整天 |
| 历史连续性 | 最近若干完成批次的摘要＋少量相关互动偏好 | 摘要可能丢细节；失败批次会影响覆盖；不是按当前话题自动检索上午所有摘要 |
| 按需回读 | search_messages / query_timeline / query_person_history / search_history_summaries / read_context | 需要本轮选择并成功读到；原话精确语义召回不是当前向量索引的覆盖对象 |

现有向量索引主要覆盖已提交认识与历史摘要，而不是每条原始聊天。FTS trigram 是词面／子串检索，不是理解整句意图的语义记忆；两者要按明示的检索模式组合，不能混称。[S03][S04][S05][S06][E01]

### 例子：原文保存了仍可能答不出

09:20，群友甲说“周五下午三点在图书馆门口集合”，Bot 沉默。16:00，甲问“上午说的集合是几点？”

当前系统有机会从原话或摘要回查，但不能保证这条上午消息仍在近期窗口，或摘要保留了时间，或 Agent 在有限轮次里选了正确检索。不能把模型说“想不起来”直接解释为数据库没有该消息。

目标不是把“沉默”改成“也回复一句记住了”，而是让 16:00 的问题可以稳定走同群时间／人物／主题定位，回读真实原句并核对之后是否改约。

## 3.4 本轮不采用的极端方案

不把全部群史塞进每轮；不每条消息额外调用一个意图分类模型；不把关键词命中当发言命令；不把所有普通聊天自动写成永久人物事实；不开放跨群记忆来补本群召回；不让模型自己声称已经读过未展示的资料。

# 4. 应当大胆改的，是产品表面与认知接口，不是把后端全部推倒

## 4.1 当前前端问题不是“多几个页面”这么简单

现有主导航按插件、模型、认识、技能、群、任务、系统设置划分，系统设置本身还有多页签；群页面再列所有插件和 schema，并用文字解释全局启用、群启用、授予、额度与当前运行状态之间的关系。[S13][S20][S21]

以“让本群使用 Python”为例，用户需要知道：workspace 是插件、worker/gateway 是另一个层次、该群需有插件记录、实际权限按主体与角色判断、对话只看到可委托能力、模型还要建立 work。把这些内部分层逐项做成表单，并不等于完成了可用性设计。

**判断：需要一次真正的信息架构重组，而不只是继续给每个插件加说明段落。** 插件继续作为代码扩展与业务封装单位；“能力”成为运营者的主要操作单位。高级功能后置而不删除，符合渐进披露的基本做法。[E02]

## 4.2 目标导航：六个一级入口

| 一级入口 | 主任务 | 不再放在这里的东西 |
|---|---|---|
| 总览 | 当前可用能力、需要处理的问题、正在做的工作、最近真实交付 | 全部参数、长 Trace、插件生命周期细节 |
| 群聊 | 看群消息、为什么回复／没回、本群参与方式、播报订阅、允许能力 | 无关全局凭据、全部插件 schema |
| Agent | 人格与表达、参与方式、睡眠、公共研究、工具能力与授权引导 | 装载器目录、原生函数签名作为主要操作 |
| 工作与交付 | 信息工作、提醒、待交付、文件、取消／恢复、真实结果 | 把心跳内部 task 当普通用户提醒 |
| 记忆与资料 | 本群原话、摘要覆盖、已确认认识、公共兴趣、方法技能、媒体资产 | 不同资料类型混为一个“记忆列表” |
| 系统 | 模型与连接、额度策略、执行后端、账号／权限高级管理、插件开发、诊断 | 日常用户必须先理解的内部术语 |

具体 route 可变；原资源 ID、历史事件、业务归属与权限语义不可变。确有用户在用的深链可以通过单次路由映射到同一新编辑器，不保留两套写入页面或平行业务接口。与过去“只调导航、不改页面”的限制不同，本轮明确允许对组件与接口投影做必要重构。

## 4.3 能力页展示“能做什么”，不是“装了什么”

初始能力卡按用户任务组织：网页与公开资料、Python 与文件分析、浏览器、直播日历与播报、群报告、公共研究与分享、媒体片段、文件交付、账号操作、可选 Core。

每张卡显示五类独立事实：

- 代码支持的动作与适用入口：直接对话、委托工作、系统周期或人工操作。
- 部署／连接条件：例如本机试用、Gateway 未运行、目标平台不支持此上传协议。
- 全局保存与当前运行值：是否已经应用，是否需要显式重新加载。
- 当前对象的使用资格：本群、所选发起者、具体能力和额度，不用一个笼统绿色开关代替。
- 最近验证：哪个 source/job/execution/action、在哪个后端、何时成功；没有记录就显示“未验证”。历史成功不保证永久健康。

状态是多个事实的组合，不能把所有失败都叫“未启用”。“已注册工具”最多说明注册成功，不能展示成“业务可用”。

## 4.4 一份配置真相，多个任务视图

不新建 capability_settings 数据库或第二套授权平台。RootConfig、PluginSpec、当前装载状态、现有 CapabilityAuthority、ProviderRegistry 与实际执行记录继续是事实来源。[S09][S14]

允许新增一个小型只读能力投影，例如 `RuntimeQueryService.capability_status(scene_id, subject)`。能力用途、背后的工具与插件、部署要求由已有声明扩充少量展示元数据得出；当前是否允许执行仍调用原判定，不由前端复制一套规则。

能力启用引导提交的是显式的配置变更清单：改哪段、旧值是什么、涉及哪群、是否授予新权限、怎样生效。整个根文件仍统一校验和保存。配置已保存但某插件重载失败时分别呈现，不自动换后端、不悄悄恢复旧业务。

常用页和高级页复用同一草稿与同一写入合同。未动字段原样保留；秘密值只允许保留／替换／清除三种明示操作；不让页面把空值默默解释为撤销或无限。

## 4.5 三条配置向导

### 向导 A：让本群使用 Python

选群 → 展示已配置计算后端与限制 → 确认在本群开放 → 显示怎样发起委托与运行核对入口。后端缺失时直接指向该能力的连接设置；没有群专属参数时不要求填空 JSON。启用不自动运行脚本，不更改出网或文件发送权限。

### 向导 B：定期公开研究、只在指定群分享

研究开关／主题／系统额度／公开资料范围，与“哪些群允许分享、每天几次、睡眠如何处理”分两步展示。UI 将真实系统主体绑定为当前实现的 scheduler/heartbeat，不要求用户猜 `principal_id`；保存前展示拟生成的授予。无分享群时允许研究但不发布，无研究授权时不靠全局插件开关绕过。

### 向导 C：给这个群增加播报

选直播／动态／日历等服务 → 选已登记对象 → 显示全局来源是否可用 → 设置群频率和 @全体资格 → 预览影响并保存。“关闭普通聊天”本身不叫“配置完成播报群”。

## 4.6 群聊页成为调试行为的主要入口

点击一条消息即可看到：存储成功、是否有资格、进入哪次机会、是否排队、进入了哪个模型窗口、模型选沉默还是提交失败、对应哪条真实回执。原始 source ID 作为高级展开，不要求用户先去日志抄 UUID。

群设置将常用项目缩成参与方式、允许能力、播报、睡眠和记忆隐私；模型供应商、代理、UID/卷、原始 schema 在系统页或能力高级页中。全局默认与本群覆盖显示具体来源，避免“一个开关在哪里都能改、改了又不知道谁覆盖谁”。

# 5. 认知与调度改造：从“机械门槛多”变成“可解释地及时参与”

## 5.1 先让延迟可以分解

**涉及模块：** `events/builder.py`、`scenes/actor.py`、`runtime/agent_runtime.py`、`cognition/context.py`、`cognition/gateway.py`、`actions/queue.py`、`web/query_service.py` 与群消息详情。

沿已有事件和 Trace 增补必要的时间点，而不是新增一套监控平台：

```text
本机收到 → 原话入库 → 机会判定 → burst 等待 → 模型名额等待
→ 上下文准备 → 第一次模型请求 → 工具与后续轮次
→ 提案提交 → 排队／延期 → 实际尝试 → 平台回执
```

本地耗时用单调时钟；源站消息时间与本机接收时间分别保存，避免把时钟偏差当模型耗时。复用已有 `queue_ms`、`send_ms`、context_plan、已读范围和 call_id，缺哪一段才补哪一段。

页面必须能区分：`没有认知机会`、`等待资源`、`已观察并沉默`、`关键原话未装入`、`预算拒绝`、`提案冲突`、`睡眠延期`、`已尝试未知`、`实际送达`。这些是现有事实的投影，不是新的可编辑状态。

**建议验收目标，不是当前测量结果：** 在没有队列拥塞、仅短文本、无外部附件读取的指定联调环境，直接 @ 的本地调度阶段以 500ms 内为初始目标；若达不到，展示实际超时阶段。供应商响应、工具网络时间单独计量，不向用户承诺总响应必为某个固定秒数。比较 P50/P95、每轮输入 token、协议拒绝率、沉默率与误接率，不能只看消息总数。

## 5.2 建立快、慢两类机会，但只保留一个社会决策入口

**快入口：** 直接 @、回复 Bot、明确称呼下的直接问题、正在等待的答案、取消／纠正／停止。这些优先获得短合并窗口，不排在非必要维护与自主研究后面。快不意味着绕过当前群资格、睡眠叫醒确认或权限。

**普通入口：** 群友相互聊天、关联话题与弱机会。按群的参与策略和预算形成有限观察批次，使用同一个 SocialCognitionCore 判断说或不说。连续话题可以获得短时关注，但新兴趣不能自行变成工作授权。

**禁止实现成：** 每条消息先买一个分类模型，然后再买一次正常回复；在 Python 中设置几十个语义关键词并声称已经理解群聊；为了“热闹”强制某个周期发话。

本群提供“安静／自然／积极”预设只是编辑现有或明确新增的少量参与参数。保存前展示实际变化和预计调用机会，不通过一个预设悄悄启用联网、发布或跨群资料。预设推荐值应根据这一项目联调数据校准，不把本报告中的示意阈值写成强制生产默认值。

## 5.3 缩短当前对话的关键路径

1. 当前直接请求和其必要引用先装配，旧失败工作、全量目录、无关人格样例不能压掉它。
2. 强证据图片按需读取；仅用于发送的已授权运营表情不应为了展示目录预先下载全部像素。
3. 模型实际请求前再取一次当前 Scene 快照；等待模型名额期间新到的直接问题不得使用过早冻结的窗口。
4. 同一事项追问通过既有 mailbox/observe 合并；取消与修订控制优先处理。不要机械中断并重开每次模型请求，避免重复费用和重复副作用。
5. 准备长任务时优先建立真实 work；对明确说“用 Python／生成文件／实际浏览器”的请求，不使用相邻计算器或 HTTP 页面工具冒充完成。普通短计算仍可选择最短路径，不要求所有问题都建 work。

**对失败的处理：** 已发生模型／外部调用的结果保留；仍有预算时在同一执行中根据明确错误修正。预算耗尽或传输未知时给出可追踪的未完成状态，不无声吞掉，也不自动购买新预算重复整个请求。

## 5.4 热话题上下文是短期投影，不是永久人物记忆

在现有场景状态／Trace 可承载的范围内保留小型投影：当前相关来源 ID、参与者、未回答的直接问题、最近 Bot 处理的来源、仍有效等待和短期话题窗口。只存事实关联和可重建的定位，不记录长链思维，不编造“置信度 0.97”。

正文仍从原话账本读取。弱机会处理后的沉默可以结束这个观察机会，却不能删除原文，也不应该把全话题永久加入黑名单。

# 6. 历史回忆改造：让“上午那件事”有一条短而可靠的路径

## 6.1 新增一个面向模型的窄复合读取入口

建议提供 `recall_chat`（名称可调整），复用已有搜索、时间线、人物定位、摘要索引和原话读取，不再要求模型为了一个普通追问自行拼接多层内部 ID。

**建议参数：**

| 参数 | 含义 | 边界 |
|---|---|---|
| `query` | 要找的事项或关键词 | 不作为 SQL/FTS 语法直接执行 |
| `time_range` | 明确起止或受控日期段，例如“今天上午” | 由已配置业务时区解析；歧义保留，不猜缺失时区 |
| `speaker_ref` | 可选的本群实际人物引用 | 不从模糊昵称自动认定唯一身份 |
| `limit` | 需要的少量候选 | 受既有读取／请求容量约束 |

对话默认仅展示这一复合回忆入口和必要的原文续读；底层时间线、人物历史等函数继续复用，完整低层 schema 在需要时再展开，不把新工具叠加成更大的初始工具清单。

返回同群候选的时间、发言人、原始 event_id 对应引用、真实片段、未展示范围、为什么匹配和继续读取位置；默认不能返回其他群资料。精确引用仍只来自已展示原文，不把摘要当逐字引用。

这是读取能力，不授予保存认识、发消息、建立工作或跨群能力。

## 6.2 检索顺序与费用

先利用显式回复关系、人物与时间窗口缩小范围；再用本地词面原话与已有摘要／认识索引定位；需要精确事实时回读原句和之后的纠正。

语义模式必须保留现有本群 opt-in，未经同意不向外部 embedding/rerank 提交群文本。未配置语义检索时明确为本地模式，而不是假装已经语义理解。若设计为词面＋语义共同检索，二者应事先作为同一公开合同，语义失败时说明未完成该部分，不暗中换成另一种结果并称完整成功。

不要每条群消息自动检索。**初始关联召回只发生在已经准入的社会轮次，默认至多一次；进一步读取由同一 Agent 在原预算内明确发起。** “上午／刚才／你上次说”等历史指向、已有 reply 链或当前未决事项可以成为触发依据，无历史关联的“你好”不需要查一整天。

## 6.3 先用已有索引，再决定是否增加原话窗口索引

第一版直接复用现有 `memory_index` 对摘要／认识的检索，加上原话时间与词面搜索。先验收“上午那件事”，不要同时引入新向量数据库、全量对话 embedding 和新摘要模型。

只有实际观察表明大量必要细节没有进入摘要、词面表达变化导致明显漏召回，第二步才扩展原索引的 `source_kind` 为有限原话窗口。每个窗口必须带 scene、事件范围与源修订／有效性，向量只是可重建定位；原文权限与原句才是事实。解释这份索引解决的具体缺口和额外费用，不把所有原话自动转成永久记忆。

窗口索引的创建可以依附已有批次维护或明确人工重建，不为每条消息新建一个模型调用。删除／权限变化／索引覆盖不足均需真实可见；不篡改原始事件时间。

## 6.4 修订和否定优先于“相似度最高的一句话”

原话可能是计划、玩笑、否定或之后被纠正。回忆结果应至少保留说话人、时间、相邻语境，以及本轮范围内可定位的后续更改；不能只因某一句更相似就忽略“改成四点了”。

遇到两个人同名、多个上午、同一天多个集合安排，先展示候选或询问唯一必要歧义，不自动选一个。没有原话支持时回答未查到，不能把角色设定或自己的旧回复补成群友曾说过的话。

## 6.5 上下文容量优先级

不硬编码整天原话比例，而用同一个实际 token 装配器：

```text
本轮直接原话／必要引用
→ 当前事项状态与刚召回的相关原文
→ 本轮工具结果
→ 相关已确认偏好与历史连续性摘要
→ 可选人格例子／媒体目录／无关旧事项定位
```

每部分有可解释上限，最终以完整请求成本为准。已召回但没放入最终模型窗口的材料不算已读。大量旧失败任务只保留计数和可定位入口，不挤进当前聊天主体。

**验收的核心不是模型偶然回答对一次，而是能展示：哪个原话范围被定位、哪一段进入了这次模型请求、答案依据是什么。**

# 7. 简化模型接口：把宿主能算的关系拿回宿主，不削弱事实约束

## 7.1 为什么有必要

当前 `respond` 同时涉及消息、来源去向、ack/operation/delivery/work 引用、收件人、显示引用、期待回复、下一步、未完成项和注意力释放；工具目录又包含大量本地读取与管理 schema。[S22]

很多概念在底层是必要的，但不代表都应该在每次普通短回复中要求模型再次拼对。联调记录里的旧提醒与新 Python 提案一同回滚，说明这类组合负担已经影响业务，不只是代码风格偏好。[S01]

## 7.2 确定采用的方向

- 明确保留人类原话、实际收件人、显示引用、工作版本和交付身份的区别；禁止把它们因为“简化”合并为错误的一个字段。
- 但重复的、可由已登记动作唯一推导的状态交由宿主生成。模型选择“回复哪条已读请求／交付哪个当前可交付结果”；宿主填充已绑定的工作 ID、修订、原请求者和回执关联。
- 对模型表达的业务意图采用互斥结构：普通回复、创建确认、操作确认、工作交付、文件上传、显式沉默／等待。避免让一个对象同时暴露多种互斥 ref，期待模型自行排除所有非法组合。
- 每次只暴露当前有效的操作形状与候选引用。没有可恢复工作，不展示恢复参数的复杂枚举；有可交付成果时给确定的交付句柄，不让模型从“可编辑任务”里猜。
- 保留原提案暂存与最终事务。创建＋承诺确认、修改＋操作确认等必须一起成功。独立来源尽量用明确 checkpoint 分开，不把无关旧提醒与当前新请求绑定在一个失败域。
- 无效提案在明确工具边界返回可操作错误；不自动修参数，不静默丢弃一项再称全部完成。不可恢复冲突仍保留事实，不通过取消校验制造成功。

## 7.3 范围控制

不换 Agent 框架，不移除 work Agent，不增加常驻 planner/router 模型。先重构 schema 的对外表达与宿主派生字段，复用 `ProposalLedger`、`TurnReferences`、`RuntimeGate`、事务与回执。

需要切换对外工具 schema 时直接按新合同改生产者和消费者，关闭同名双语义入口。已有持久数据保留原格式解释，只有确实需要的离线转换一次完成，不把运行时堆成新旧两套兼容分支。

**完成条件：** 普通单句回复不需要无关的工作／提醒字段；创建工作无需模型发明句柄；本轮交付只能选择真正可交付事项；未读原话仍不能用作证据；相同输入下协议拒绝次数和提示／schema token 有实际下降记录。

# 10. 数据、部署与项目复杂度边界

## 10.1 不做破坏性“清理”

不 Reset，不删除已提交认识、原话、模型消费或未知执行记录来制造无错误状态。历史失败批次先核对是否已实际提交；未知发送保留原身份；旧工作成果保留可回读。删除无用 UI 概念不代表删除对应历史事实。

本机新输入目录可通过下一次执行的新结构隔离；旧目录只按明确的所有权和保留策略回收。真实产物、延期资产与临时输入的生命周期不能混合。

## 10.2 一个正式执行后端，不是两套业务系统

正式隔离执行采用原计划的 Gateway；本机 driver 若保留为开发用途，使用同一宿主准入／记录／结果合同，界面显式标明开发状态，不作为 Gateway 故障回落。若不再需要开发 driver，应在完成必要切换后明确删除，而非长期维护安全语义不同的两条正式链。

不为了调通让 LenBot 隐式获得 Docker socket、账号 Cookie 或控制网络。部署放行与普通源码改动分别授权。

## 10.3 关于参数数量

不以“去掉参数”牺牲真实约束，而以业务层预设、少量常用字段和高级展开降低日常负担。每个可调参数必须回答：谁会在什么问题下改它、怎样生效、单位与边界是什么、与哪个其他参数联动。回答不出且没有真实需求的参数才合并／删除。

默认／覆盖是**一个解析函数**产生的结果。上下文预算、执行期限、累计模型次数、token 授予、日额度、群发布次数不能因界面简化被合成一个模糊“资源值”。

## 10.4 文档只维护现在

保护总计划与人格来源；当前任务页只写当前状态、这轮未决项和下一步；架构页解释当前真相，运维页解释真实部署。已经关闭的旧任务计划从工作树移除，历史通过 Git 查看。

本文作为一次施工材料可保留到任务结束，结束后只合并仍有效的产品与架构决定。不要把本报告、上一份报告、每轮对照表全文一层层追加回 docs。
