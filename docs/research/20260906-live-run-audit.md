### 3. 普通聊天承担了过重、部分未充分表达的输出契约

每轮提示携带同一份输出 schema：精简序列化后 9,657 字符、21 个定义、125 个属性出现位置。绝大多数是可选字段，但普通闲聊仍需从这一整套结构中选择表达和状态更新。

已经有具体的契约问题，而非仅凭长度猜测：

- `WorkingPersonUpdate.source_event_ids` 在 JSON schema 中没有条件必填约束；Python validator 却要求人物理解发生变化时提供。前两次 Omen 闲聊均在这里失败并多调用一次模型。

- 一次输出甚至带回 `$defs`，导致再次修复。
- “撕咬”这类简短互动也出现一个仅包含回复元数据的空消息提案，被校验拦下。

格式校验的存在有价值；问题是模型可见契约、内部状态结构和普通表达负担没有协调好。第一次和第二次轻量闲聊分别消耗约 44 秒和 67 秒模型时间，均执行三次模型调用，包含一次格式修复和一次最终续接。不能把这些耗时全部算作正文写作。

## 参考聊天的“人味”来自什么

运营提供的“一星花花”节选中，KTV 这段先抓住“行业里总有一个把歌唱得很投入的人”，再接“碰杯叹气”。两句话围绕群友经历构成同一个具体场景，附图补充调侃和共鸣的语气。它没有为参与话题而声称自己拥有某位前同事，也没有把话题转成自己的角色履历。

知识问答与闲聊的节奏也有所区分：先给模型用途，再补部署特点；被追问术语后解释该术语。可借鉴的是接住对方当前关心的部分、补充有意义的具体内容、将情绪表达交给合适的文字或图片。

这份节选不能证明其中“跑分过关”“数据还没放全”等知识结论准确，它没有给出可核对的基准、数字或来源。其事实内容不能直接用作知识正确性的标准，也不能据截图推断其后端架构或模型水平。

## 当时的修改优先级与待核对项

1. **先处理参与和能力判断。** 在 Social Core 中明确当前对话对象、群友是否愿意继续互动和 Bot 实际可参与的事项。面对含抵触的模糊信号，保留不确定性并给对话留空间。角色兴趣体现在关注点和措辞中，实际能力和共同经历按证据判断。
2. **收敛持续认识。** 区分“Bot 说过某句话”和“双方确认的事实”；工作认识保留对后续判断有用的变化，减少将临时自我表演当成持续意图。继续通过获准提案更新，原始事件保持可追溯。
3. **简化并补全模型可见契约。** 统一相近的话题字段，明确更新时所需证据，普通接话使用最小输出；完整权限、任务、事务与发送校验继续由 Runtime 保持。先减少这批真实的格式修复，避免额外增加每轮必跑的表达模型。
4. **把表情作为表达选项。** 在文字、表情和混排之间按语境选择，提供简短、真实且按场景隔离的素材概览及检索后发送示例。查找和发送仍由模型提案与 Gate 决定。
5. **最后决定模型取舍。** 对需要决策的少量原始问题固定实际输入与配置，隔离核对模型的推理、语义理解和工具选择。只有在条件一致时，才判断差异主要来自模型。当前数据足以判定本次输出不合格，尚不足以断言换一个模型即可解决整体互动效果。

此外，失败提交应能从 trace 定位具体拒绝原因和待审计候选；这次泛化的提交错误限制了首轮数学题的归因。上述是下一轮建议，本次审计没有应用行为修改。
