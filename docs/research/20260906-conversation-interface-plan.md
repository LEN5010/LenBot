## 目标与范围

1. 普通文字、单图、图文混排均能用更少的必填语法提交，成功路径继续只需一次模型调用。
2. 无工作、无提醒、无等待、无在途发送的轮次，不携带这些空状态的长篇解释。
3. 有工作结果、失败、未决事项或发送状态时，模型仍能准确区分其含义。
4. RP 保持角色口吻；减少主动插话与增加参与时的表情选择分开处理。

本轮设计不修改数据库结构、事件追加、SceneActor 单写、场景权限、事务、真实送达语义或工作预算。不引入固定 Planner/Replyer、不让普通模型正文直接发送、不更换提供商或模型，也不自动恢复已删除的人工表达样例。

## 改动 1：缩小模型输出契约

### 片段只写内容，类型由字段确定

保留 `finish_turn`、`messages`、消息顺序和 `segments`。单个片段使用一个内容字段：

```json
{
  "messages": [
    {
      "segments": [
        {"text": "哼哼，眼光不错嘛"},
        {"image": "P07"}
      ]
    }
  ]
}
```

这只是接口示意，不加入运营样例库，也不作为固定回复。

- 文字：`{"text":"一句回应"}`。
- 图片：`{"image":"P07"}`，也可以是本轮已提供的 `I` 引用。
- 单图：一个仅含图片片段的消息，不要求附加文字。
- 混排：按数组顺序发送，继续支持图前文字、图后文字及现有数量上限。
- 沉默：`{"messages":[]}`；仍可同时提交已经暂存的合法认识或工作。
- 每个片段必须且只能有 `text`、`image` 中的一个；空片段、空内容、同时出现两个字段及其他字段均拒绝。

模型不再填写 `type`，也不再把短图片引用放进名为 `asset_id` 的字段。`ProposalLedger.finish` 验证新契约后，确定性转换为现有内部 `MessageSegment(type, text, asset_id)`；转换图片时仍通过本轮引用表解析，再经过 Gate 和发送前校验。原生 assistant 续接、工具调用 ID 与供应商签名不改写，转换仅发生在提案入口。

这是一套替换后的模型契约，不添加 `media_ref/image_ref/asset_ref` 多种拼写兼容，不猜测缺失内容。存量事件、回执、人工样例和 API 使用的内部片段结构保持；人工样例投影到模型上下文时统一转换成新契约。

### 工作与履约关联继续明确

`reply_to`、`ack_ref`、`work_ref`、`delivery_ref`、`expect_reply` 的语义保留，普通聊天可以全部省略。`note` 继续可省略，不要求模型每次解释为何参与。

不从自由文字猜测“这句话确认了哪个工作”，也不以一条消息包含“查好了”来自动完成任务。`ack_ref` 对应真实暂存提案、工作版本校验、失败不能履约和真实回执确认等规则继续生效。

初版保留了同批新建与确认。18:06 Reset 后的真实运行显示，模型会只编造 `ack_ref` 而漏调 `start_work`，并重复失败；后续修复改为工具生成引用，收到暂存回执后才在 `finish_turn` 中开放对应 `ack_ref` 枚举。新建事项的确认通常需要两步，普通聊天仍可一步结束，事务与发送边界保持不变。

### 给服务方的 Schema 使用清楚的基础结构

目前直接发送 Pydantic 生成的 Schema，包含 `$defs/$ref`、`discriminator` 和多层联合。新片段不再需要判别联合：对外是包含 `text`、`image` 两个可选字符串字段的普通对象，禁止额外字段；“恰好一个内容字段”由本地严格校验，并在工具说明中明确。

终结工具的对外 Schema 明确编写并内联其小型对象结构，不把 Pydantic 的展示标题和实现细节全部带给模型。内部校验仍为权威，不能因提供商接受请求就认为其实施了约束解码。

实施时用当前 BotCF 路由核对普通对象、数组与可选字段的实际表现，不盲目开启未经验证的 `strict` 参数，不增加自动提供商兼容分支。服务端是否强制所有 Schema 约束是待核对事项，不是此方案成立的前提。

### 参数修正只回传具体问题

将长 Pydantic 异常转换为有界的路径、原因和正确结构提示。例如指出 `messages[0].segments[1]` 需要 `{"image":"P07"}`，而不是重复整个 Prompt、文档 URL 和内部类名。只使用本轮已有引用，不通过错误提示授予新的图片或消息权限。

修正仍最多一次、占用原预算，已经暂存的提案不重复执行；修正失败不发送部分候选。提交冲突不走参数修正。原始失败原因保留在脱敏 Trace 中。

## 改动 2：按实际情况组织上下文

### 稳定的短规则与按需的运行资料

主提示保留角色身份、相处方式、参与原则、证据边界、当前时间和终结方式。建单步骤、恢复规则、履约字段及资料读取方法放在相应工具说明与回执中，减少在主提示和事实消息里的重复。

不将精简理解成删除角色，或把所有回答压成短句。角色仍可调皮、认真或只用表情，篇幅由当前要表达的内容决定。

| 材料 | 提供条件与保留内容 |
|---|---|
| 群友原话、自己的真实已发送消息 | 继续按自然时间顺序使用原生 user/assistant；保留人物、时间、引用和图片归属 |
| 明确相处要求 | 仅有有效记录时提供；保留主体、陈述、依据类型与来源引用，避免将其当成必须宣读的台词 |
| 工作 | 有相关工作时提供目标、实际执行结局、回应阶段、摘要、未决项、资料引用及能否恢复；详细约束和预算按需读取 |
| 提醒、等待回应 | 有实际记录时提供目标、内容、时间或当前状态 |
| 已获准表达和新回执 | 有记录就提供正文与准确状态；即使没有工作也不得省略 |
| 运营表情目录 | 保留当前 20 项文字目录与一张总览图，允许直接选用；其余素材仍可搜索 |
| 人工样例 | 库中实际存在才提供，使用新输出格式投影；不自动补回旧样例 |
| 本轮输入范围 | 简短标明哪些是新收到的消息，继续使用真实读取截点 |

工作、提醒、等待和发送事实均为空时，整个运行事实块省略。只存在某一类事实时仅展示该类及必要解释。例如有 pending 表达就说明它已获准、尚无回执；出现 unknown 就保留不得自动重发的含义。

绝不能在精简时再次混淆 `result_ready` 与执行成功，或者把失败搜索、单次算式当作完整结果。工作结果里的未决项和失败原因属于必要信息，不能当作噪声删除。

`facts_message` 的拼装与工具可见性使用同一份本轮状态视图。详细完整记录仍在数据库中，`query_jobs/read_tool_result` 可继续读取；模型短引用背后的真实 ID、版本与读证据集合由运行时维护。

### 只隐藏没有操作对象的管理工具

首轮保留现有九个本地读取工具，以及 `start_work`、`schedule_reminder`、`remember` 和 `finish_turn`。完全没有可操作对象时，从当前 22 个工具减至 13 个，不根据群消息关键词猜测是否需要查询或记忆。

其余工具按已提供的真实对象展开：

| 工具 | 可见条件 |
|---|---|
| `revise_work/cancel_work` | 本轮存在对应可操作的工作引用 |
| `resume_work` | 存在标记为可恢复的工作 |
| `update_reminder/cancel_reminder` | 存在已提供的提醒引用 |
| `refute_memory/supersede_memory` | 已提供可修订的认识目标 |
| `resolve_wait` | 存在已激活的等待回应 |
| `discard_proposal` | 本轮存在尚未提交的暂存提案 |

每次模型调用前重新计算可见工具：读取工作或认识、暂存新提案、吸收新事件后，相应操作能够在下一步出现。可见性不等于授权，执行时继续验证来源、状态和版本。已曝光但过期的对象不能因工具可见而通过校验。

最后一步继续只开放终结工具。新建工作与终结所需的字段从第一步就可用；固定终结接口不随可见工具增减反复改形状。

### 表情使用与主动参与分开

运营当前反馈为“主动回复过多，表情反而偏少”。因此本次不再减小素材目录或给图片加次数配额。

已将原有“连续配图后换文字”“通常一处一张”的一般性偏好改为按当前表达需要选择：文字、单图和混排都可以构成完整回应。决定参与后，允许一个合适的表情独立完成这次接话，不必另外编一段解释。

减少无关插话属于参与策略，不能通过限制每次回复里的图片来替代。也不要求每条消息机械带图或固定图文比例。

## 昵称呼唤：作为独立的参与调整

运营提出可以检测“然比”“小然”，平时少发言。本轮采用“被叫优先、普通群聊以旁听为默认”的方向：

- 提取当前消息中的显式 @Bot、引用 Bot 消息、运营配置的昵称命中，作为可核对的呼唤线索；昵称初始值采用本次提出的“然比”“小然”。
- 设置页支持编辑额外昵称；保存值优先，省略保留、空列表清除额外昵称。私聊标为直接消息，机器人名字也参与匹配；CQ 片段和引用原话不参与昵称匹配。
- 命中表示可能在找 Bot，不等于必须回复。“然比的表情包”这样的第三人称讨论仍需要 Social Core 看语境。
- 正在与 Bot 延续的互动、已建立工作的结果和真实提醒，不要求用户每句话重复昵称。
- 未呼唤且属于别人之间的新话题，默认旁听，减少对每张图片的主动点评。
- 这些线索不决定台词，不新增独立的参与判断模型；同一 Social Core 继续判断对象、承接和沉默。

本轮独立落实了呼唤线索、配置与默认旁听，没有增加基于词表的硬拦截。若后续还要减少未被呼唤时的模型调用，需要另外设计唤醒与未读输入的调度：所有消息仍应入库，不能将跳过调用的输入伪装成已认知，不能截断正在继续的对话。

昵称匹配是本次运营提出的显式呼唤机制；实施时应同步说明工程约束里“呼唤线索”和“用关键词替代社会判断”的区别。

实际服务核对只使用合成对话、简短测试角色与纯蓝色测试图片，复用当前模型连接，在隔离库和 Shadow 中运行，不连接 OneBot。没有向外部模型发送生产群聊、人格或素材。保留候选与真实调用信息，不建立固定消息数、评分或批量模型对照门槛。

预期收益是减少格式修正和无关说明，保持或降低模型往返次数。一次正常模型响应的耗时仍受提供商影响，不能承诺所有回复降到某个秒数。自然度、主动参与和表情是否合适，仍需后续恢复后的具体群聊判断。

提示分隔与示例的通用依据见 [Google 提示设计文档](https://ai.google.dev/gemini-api/docs/prompting-strategies)；它不证明本方案对当前兼容服务有确定收益。当前事实与历史问题另见 [ADR-0044](../adr/0044-native-conversation-and-evidence-ledger.md)、[首轮实群记录](20260906-vnext-live-followup.md)、[工作失败审查](20260906-work-failure-review.md)。

## 本轮核对结果

相关对话、提案、发送状态、工作、媒体、场景事务与设置共 93 项检查通过；前端构建通过。实际检查了隔离设置页的昵称保存、分隔与去重、刷新后保留，以及运行记录页的新格式单图提案。测试面板已关闭。

| 指标 | 修改前 | 修改后 |
|---|---:|---:|
| 工具数量 | 22 | 13 |
| System 字符数 | 1404 | 814 |

这是使用同一项目估算方法测量输入体积，不是提供商账单 tokens，也不是完整生产上下文或响应速度对照。

合成模型核对中，“小然，可爱捏”得到文字提案，两个群友相约游戏时选择沉默，“然比，发目录里的蓝色方块图片就行”得到单图提案。三次均一步完成、没有格式修正，局部运行耗时约 2.6–3.3 秒；没有真实发送。测试使用简短角色和一项合成目录，不能拿它与生产的大目录、真实人设和群聊耗时直接比较，也不能据此宣布实群自然度已经达标。

原计划读取备份中模型配置、角色与运营素材的外部核对被自动审批审查拒绝，理由为担心真实群聊外发；该脚本未执行。随后收紧为仅从生产库读取模型连接配置，其他输入完全在脚本中合成，经审批后完成上述核对。
