# 上下文装配

每轮对话的请求怎么拼出来，为什么窗口是锯齿形，以及被丢掉的原话怎么取回。行为边界见[当前架构](architecture.md)，参数改法见[运行手册](operations.md)，本轮实测见[当前任务](iteration.md)。

## 一、轮次之间不累加

没有一个会持续增长的会话。**每一轮都重新拼一份完整请求**，信息从四个互不相干的地方流进来：

| 来源 | 内容 | 谁决定它的大小 |
|---|---|---|
| `persona` | 人格与角色资料 | 人格文件，固定不变 |
| `recent_history` | 群里真实说过的话 | `conversation_recent_tokens` |
| `original_input` / `related_original` | 本轮要处理的原话，完整原文加图片 | 与上一行**共用**同一份预算 |
| `history_summary` | 最近若干条已完成摘要，打成一个 JSON | `conversation_summary_limit` |
| 认识 / 媒体目录 / 运行状态 / 工具定义 / 预算 | 参考与易变资料 | 各自的上限 |

**摘要不进窗口，也不替换窗口里的原话。** 它是与窗口平行的另一块参考，标着 `evidence: locator_only`——只能定位，要精确原话仍须回读。

`recent_history` 由 `pack_events` 从**最新一条倒着往回装**，装到预算用完就 `break`。所以窗口的头（最老那条）不是谁指定的，是"倒着数到哪儿就是哪儿"。本轮输入越大，留给历史的越少，头还会额外前移。

## 二、出场顺序就是缓存顺序

```python
messages[:] = [*stable, *window, *brought_in, *volatile]
```

`STABLE_SECTIONS` 只有 `persona`。`window` 是原话窗口，`brought_in` 是引用带进来的旧原话，`volatile` 是其余全部——**摘要块在这里，在最后面**。

供应商只复用到第一个与上次不同的 token 为止，所以块按"多久变一次"排：整场不变的在最前，房间自己的时序居中，每次调用都新的在最后。**摘要块换新只影响请求尾巴，前面一个字节不动**——总结的频率对缓存没有影响。

唯一每轮都会破坏前缀的，是 `recent_history` 的头在动。

## 三、锯齿：长到峰值，一次丢掉大半

窗口若是固定大小的尾随窗口，积压会在第一轮就把它填满，此后永远处在"满了只能滑"的状态，头每轮前移，缓存从窗口第一条断。

`anchor_window_start()` 把头钉在 `conversation_window_step_rowids` 的整数倍上：

```python
boundary = ((最老 rowid + step - 1) // step) * step
dropped  = 窗口里 rowid < boundary 的消息
```

**头不动，是因为每轮都被重新钉回同一个位置，不是因为它被记住了。**
`pack_events` 每轮从最新往回重装，头落在预算用完的地方，它不记得上一轮裁到哪。
真正让头稳定的是 `anchor_window_start` 每轮把它重新对齐到同一个 `boundary`。
缓存命中完全依赖这次对齐。

因此 **`step` 的真正含义不是"一次丢多少"，而是"窗口里有没有可对齐的边界"**。
函数开头那两个提前返回是关键：

```python
if not dropped or len(dropped) == len(window):
    return          # 没有可对齐的边界，头从此由预算决定，每轮都在动
```

- `dropped` 为空：窗口整个落在 `boundary` **之上**，没东西可裁，头失去锚点
- `dropped == window`：窗口整个落在 `boundary` **之下**，同样跨不过去

两种情况都让头开始逐轮滑动，前缀每轮从窗口第一条就断。**step 必须明显小于窗口的
rowid 跨度**，窗口里才总有边界可钉。

2026-09-19 实测这条：`step=3300` 而全局 rowid 只推进 437/小时，两个边界之间相隔
**7.5 小时**；最忙的群 130k 窗口只跨 3,410 rowid，几乎等于 step，窗口里最多一个边界。
越过之后锚定连续 11 轮不触发，其中 9 轮缓存为 0。改成 `step=1000`（窗口内 3.4 个
边界）后锚定 9/9 触发，同一个群的命中回到 86—98%。

于是窗口呈锯齿：**头被每轮重新钉在 `boundary` 上，窗口在尾部生长，越过下一个边界时
缩掉一段**。齿越浅越密，头越稳，缓存越好；丢掉的那段不再出现在请求里，要用只能召回。

## 四、三个数互锁，不能单独调

裁剪不是无条件的。要丢掉一段原话，必须在**本次请求里**找到覆盖该区间的摘要（`_summary_ranges`），否则就是无声丢信息：

```python
if not any(... 该区间被 summary_ranges 覆盖 ...):
    self.omit('window_anchor', 'summary_does_not_cover_original', ...)
    return          # 拒绝裁剪，头回到逐条滑
```

而摘要块只装 `conversation_summary_limit` 条。所以：

> **能丢多少 = `conversation_summary_limit` × 单条摘要的覆盖量**

光放大窗口和步长，锚定会直接拒绝。

还有第四个数，而且它在前三个之前生效：`conversation_history_limit`。窗口的原料来自
`get_recent_events(limit=conversation_history_limit)`，**这是条数上限，在 `pack_events`
看到之前就封顶**。它若先于 token 预算生效，后果是三重的：

1. 窗口永远到不了 `conversation_recent_tokens` 的峰值；
2. 每来一条新消息，定长的条数窗口整体前移一条，**头每轮都在动**；
3. 窗口的 rowid 跨度被压小，跨不过 `step` 的边界，`len(dropped)==len(window)`
   直接返回，锚定**一次都不会触发**。

2026-09-19 实测到的正是这个：`limit=400` 而窗口 417 条 ≈ 49,301 token（每条 118
token），装满 130,000 需要约 1,100 条。最忙的群最近 400 条只跨 1,426 个 rowid，
远小于 `step=3300`，36 轮锚定 0 次触发。

**四个数必须一起动**，且 `conversation_history_limit` 要留在 token 预算之外当安全栏，
不能成为真正的约束。判断方式：omitted 里出现 `recent_history/no_capacity` 说明是
token 预算在约束（正确），没出现而窗口停在条数上限，说明条数在约束（错误）。

还有一条不显然的因果：**`maintenance_context_tokens` 决定单条摘要能覆盖多少原话。**
`begin_history_batch` 的 `fits()` 同时受 `history_target_tokens` 和维护请求的输入预算约束，
预算不够时 `full_block` 提前为真，批次就地截断——不是报错，是**静默变小**。摘要一小，
覆盖范围就够不到窗口头，锚定被挡。2026-09-19 把它从 90000 抬到 120000，同一批群的批次
从平均 7,410 token / 585 rowid 变成 **49,583 token / 2,835 rowid**，6.7 倍。

所以链条是：维护预算 → 批次大小 → 摘要覆盖范围 → 裁剪许可 → 缓存命中。

实测常数（本机真实库，2026-09-19 调参后）：

| 量 | 值 |
|---|---:|
| 单条摘要覆盖原话 | 49,583 token / 2,835 rowid（调参前是 7,410 / 585） |
| 单条摘要自身 | 823 token |
| 窗口里每条消息 | 118 token |
| 每条消息占 rowid | 3.56（最忙的群）— 77.67（最闲的群），rowid 全局 |
| 非 history 的固定部分 | 20,428 token |

**每条消息占多少 rowid 按群差三十倍**，而 `conversation_window_step_rowids` 是全局一个值。
这意味着同一个 step 在不同群里意味着完全不同的裁剪深度，锚定的行为也因此按群分化。

## 五、摘要有两个身份

1. **长期记忆**：它是语义索引的存储单元，是"想起很久以前某件事"的落点。粒度越细，定位越准。
2. **裁剪许可**：它是"这段原话已经有地方存着了，可以从窗口拿掉"的凭证。这里只要求覆盖，不要求细。

两者对粒度的要求相反。当前取舍是让单批覆盖一次丢弃量的一半，把维护调用数压下来；代价是索引定位变粗，**这个代价尚未测量**。

维护是后台连续跑的，不等到要裁时才摘。一旦某群的批次卡住，摘要前沿不前进，该群的锚定就永远不成立，窗口回到逐轮滑动——这条因果链已被实测：锚定 0 次的群缓存命中 16%，锚定成立的群 51–67%。

## 六、丢掉的怎么取回

被窗口丢掉的原话不会自动回来，也不该自动回来。取回只有一条路：**模型自己判断需要，然后调工具**。

| 工具 | 范围 | 语义 |
|---|---|---|
| `recall_chat` | 本群原话与摘要索引，可带时间与人物 | 字面 |
| `search_history_summaries` | 较早的已完成摘要 | 语义 |
| `query_memory` | 本群认识及其来源 | 语义 |

另有一条按关键词命中的自动注入（`seed_history_recall`），它走字面检索，结果会自述局限：命中的只是字面就近匹配，不代表本群没有别的相关历史。**它是补充，不是主路**——主路是模型自己去取。

系统提示为此明确写着：`recent_history` 只是最近一段原话，不是全部记忆；想不起来就去查，不要凭印象断言记得或不记得。

## 七、当前参数

| 项 | 值 | 作用 |
|---|---:|---|
| `conversation_context_tokens` | 200000 | 整个请求的天花板 |
| `conversation_output_tokens` | 4096 | 预留输出，`input_budget` = 两者之差 |
| `conversation_history_limit` | 1500 | 取多少条原料；必须大到让 token 预算先生效 |
| `conversation_recent_tokens` | 130000 | 锯齿的峰；也是摘要块的上限 |
| `conversation_window_step_rowids` | 1000 | 保证窗口里总有可对齐的边界；必须远小于窗口 rowid 跨度 |
| `conversation_summary_limit` | 15 | 要够到窗口头；实测头被第 2—10 新的摘要覆盖 |
| `history_target_tokens` | 60000 | 单批摘要覆盖量 |
| `maintenance_context_tokens` | 90000 | 单批要装得下 60k 原话 |
| `maintenance_output_tokens` | 8192 | 单条摘要的长度上限 |

峰值请求 = 130,000 + 24,576 + 20,428 = **175,004**，`input_budget` 195,904，余量 20,900。周期约 3,300 rowid ≈ 620 条消息。

## 八、未验证

- **锯齿的全部收益都是推算。** 峰值 175k 的请求在未命中时全价付。

- **命中率就是锚定成败，两者是同一条曲线。** 09-19 按每轮的锚定状态分组统计 119 次对话调用：

  | 锚定状态 | 调用 | 命中率 |
  |---|---:|---:|
  | 锚定生效 | 37 | **73%** |
  | 锚定被挡 | 23 | 13% |
  | 未触发锚定 | 59 | 20% |

  上游缓存本身是好的：向中继顺序连发同一前缀、交替两个前缀、以及五路并发发同一前缀，除首次冷启外全部命中（累计 17 次请求 0 异常）。未命中是本项目自己的前缀在变。
- 摘要粒度放大对语义定位精度的影响没有测。
- 改动之后模型是否真会主动调检索工具没有数据；基线是 923 轮里 2 次。
- 窗口大小与步长的比例只有一组取值的经验：步长接近窗口 rowid 跨度时，`len(dropped) == len(window)` 会让锚定直接返回，等于不裁。
