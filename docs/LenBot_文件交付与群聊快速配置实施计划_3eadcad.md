# 1. 当前基线：不再重做已完成的工作，也不能把关键断点当成配置细节

## 1.1 已有基础与运行证据

当前代码已有持久文件资产、文件检查、`prepare_workspace_file` 所对应的服务、文件行动、独立文件回执，以及发送前持久尝试；也已有快慢注意力标签、三个配置向导和按群设置。此次不应回退到旧版空壳结论。[S03—S08]

最新 `docs/iteration.md` 记载：LenBot、Gateway 与 OneBot 已启动，群里出现真实日程和普通回复；一次 Gateway Python 在容器启动前因缺少 `/usr/bin/docker` 失败，之后网关镜像补装 `docker-cli`。最后一次记录没有新的 Python 执行，不能把镜像重建算成 Python 工作复验通过。[S01]

同一记录明确：`file_delivery.enabled=true` 且存在指定成员的 `send_file` 授予，但 `onebot_file_upload=null`。所以文件可以具备资产下载基础，**QQ 文件上传仍未配置完成**。浏览器镜像、公开出口和媒体部署各有自己的未决条件；它们不是离线生成 CSV 后上传的共同前置，不要因此无限推迟文件链。[S01][S03][S04]

会话附带的 2026-09-16 日志只记录旧运行中的工具注册、连接及当时异常，没有当前 SHA，也没有完整文件上传回执。本次不用它证明最新版本仍有旧解包问题，更不把 `run_python` 注册成功当成执行成功。[L01]

## 1.2 当前确认的文件动作合同缺陷：三处要一起改

`cognition/proposals.py` 存在两个不同层面的形状：

- `TurnMessage` 接受 `intent='file'`、`file_asset_id`，要求文件独占行动，且关联原工作。
- 手写模型 Schema 没有 `file_asset_id`，仍要求每条消息有非空 `segments`。
- `terminal_definition()` 又根据当前事项重建 intent 列表，只加入 reply/ack/operation/work/delivery，不加入 file。

因此，当前存在“后端声称支持文件，但模型不能按已声明 Schema 产生合法文件动作”的直接断点。只配置 SnowLuma、只把 `file` 放回枚举、或只增加一句提示词，都不算修复。[S02]

另外，`TurnMessage` 当前有文件时直接推导 `inferred='file'`，多种关系的数量检查位于后续 `elif`；需在同批核对文件分支仍强制且只允许一个工作关系，不允许文件行动借此携带多个互斥引用。[S02]

## 1.3 当前平台适配的准确结论

LenBot 当前 `FileUploadConfig` 仅允许 `implementation='napcat'`，协议是 `upload_group_file_data_file_id`。这不意味着实际部署中的 SnowLuma 不支持群文件上传，而是项目尚未明确支持与验证它。[S03]

本次读取 SnowLuma 官方发布目录，固定提交 `bc8bb8c98fcee230453d68d9cbbb68bfb3e08319`：

- 动作为 `upload_group_file`。
- 必填 `group_id` 和 `file`；另有 `name`、`folder`、`folder_id`、`upload_file`。
- 目录描述返回 `{ file_id: string }`。

这足以确定应开发一个显式 SnowLuma 映射，而不是假装当前平台是 NapCat。但目录的发布版本不能反向证明现场运行版本；必须在获准环境读取实际版本，验证所选路径、鉴权及真实文件回执。[E01]

## 1.4 表情与旁听的当前机制

`AttentionPolicy` 先处理直接 @、回复、称呼、关注、在途互动及等待关系，再给普通消息关键词与窗口抽样机会。**抽样是每个窗口一次，不是每条普通消息一次。**提高抽样会增加观察机会，不保证每次观察都发言。[S05]

`MediaService.prepare_palette()` 已提供 tags 和近期使用情况，但描述被截到 40 字符；`ConversationContext` 的模型目录没有继续传 tags，只传名称、短描述和近期使用。模型因此可能拿不到足够的语义标签区分表情用途。这是本轮优先修正的候选呈现问题，不能直接归咎于模型不喜欢发图。[S06]

`SceneSettings` 目前只有 enabled/chat/semantic_retrieval/plugins，没有本群注意力与表情倾向字段。要真正实现按群调参与一页配置，需要增加少量明确的群覆盖，而不是在页面上显示实际只改全局的滑块。[S08]

# 3. P0：把文件上传作为完整业务交付，而不是最后一个 API 按钮

## F1. 模型能发现、准备并提出真实文件行动

**模块：**`cognition/proposals.py`、`cognition/context.py`、`runtime/job_runner.py`、`plugins/builtin/workspace/`、`media/files.py`、工作结果投影。

### 必须贯通的路径

```text
真实请求
→ 当前来源读取：专用日程工具或其他已开放工具
→ 资料 R 随原工作传递，或者工作主动读取
→ 原工作选择 run_python
→ Gateway 离线执行并固定产物
→ prepare_workspace_file：取得现有 file_asset_id，按实际请求准备上传
→ finish_work：保留结论、文件身份、来源及未完成部分
→ 对话读取当前工作与可交付文件目录
→ respond.intent=file，绑定唯一原工作关系
→ 原 Gate / ActionQueue / 实际平台
→ FILE_UPLOADED 与真实 file_id
```

不得写一个“发现关键词 CSV 就强制固定编排”的特殊插件。允许 Agent 选择合法的最短资料路径；用户明确指定工具时，不能以相邻工具的成功冒充指定工具已经执行。

### 动作形状

普通消息分支继续要求非空 segments。文件分支必须具备：

- `intent='file'`。
- 指向当前可见、实际存在且归属合法的 `file_asset_id`。
- 唯一工作关系，首次最终履约优先当前 `delivery_ref`；实际工作说明/非最终交付按既有合同处理。
- 不携带文字片段、图片、提及、显示引用或等待回应。

手写 Schema、Pydantic 模型、动态定义、解析、Gate 和出站记录必须同批一致。可以用明确互斥的对象分支，不允许以全局放宽 `additionalProperties` 或删除校验解决。

只有本轮存在可用文件候选时才展示文件形状；没有候选时说明未准备，而不是让模型发明资产。工作结果/详情投影至少提供：asset_id、文件名、字节数、格式、原工作与修订、源执行、有效期、上传准备/审查状态、已知交付结果。内部路径、凭据和文件正文不塞给模型。

### 交接检查

既有资产已保存但普通结果摘要没携带它时，通过原工作文件目录可回读，不应重新执行生成脚本。对话因没有 file 候选而选择文字回答时，Trace 要能显示候选在准备、授权、装配还是 Schema 哪一步缺失。

**完成条件：**一个合法文件动作能被模型在真实请求中选出并通过原事务；普通文字分支不受影响；合法文件不要求补一条虚构文字；未准备、过期、跨工作、跨群、多关系文件形状仍被拒绝。

## F2. 显式支持实际 SnowLuma，不增加自动协议回退

**模块：**`adapters/file_upload.py`、`adapters/onebot.py`、`config.py`、相关平台设置表单。

1. 通过当前已连接且鉴权正确的渠道读取实际 OneBot 实现/版本。WebSocket 与 HTTP 可能配置不同令牌，不把某个 HTTP 401 推断为 WS 不可用，也不为这次任务擅自替换现有连接。
2. FileUploadConfig 扩充明确的 SnowLuma 实现选项。保留现有 NapCat 路径；运行时只调用运营者选定、已核对的那一种，不轮流尝试不同协议。
3. 根据官方目录实现 `upload_group_file(group_id, file, name, ...)`；首版目标为群根目录，文件名使用持久资产 display_name。可选字段只发送目标版本已确认支持、且业务确有需要的值。
4. 严格解析 OneBot 信封。成功必须有该协议的真实非空 file_id，不能把 message_id、路径、布尔 ok 或 HTTP 200 当作文件回执。
5. `status=failed` 按明确拒绝记录；已经发出但超时、断连、回包缺少必要身份则 unknown，不自动重传。
6. 无法支持现场版本时，返回准确的缺失条件并保留资产。不要伪装 NapCat，也不要把上传流式暂存完成说成已经上传 QQ 群。

**首版路径选择：**优先使用既有持久资产目录的专用只读挂载。这与现有设计最接近，改动最小。不并行建设共享卷、公开文件服务器、base64 大文件与分块上传四套路径。确有跨主机需求再单独定义传输合同。

**解决首次核验循环：**“部署准备已核对”和“已有真实上传成功”是不同事实。若 `deployment_verified` 同时要求两者，须做明确语义收口：版本/挂载/读取资格由人工核对；真实上传验证只从文件回执派生。不能要求先有成功上传才允许第一条合法上传，也不能增加一个绕过所有权限的测试发送接口。

**完成条件：**真实部署使用 SnowLuma 自己的声明模式，同一普通发送通道可以上传一份已登记文件并返回真实 file_id；第一次验证是一次明确授权的正常文件操作，不是假回执或“能力探针”。[S03][E01]

## F3. 三段文件路径分别核对

| 文件所处位置 | 所有者与用途 | 禁止混用 |
|---|---|---|
| Gateway 工作区/不可变产物 | 执行输出与按身份回收 | 不直接交给 QQ 适配器作为主机路径 |
| LenBot 持久 file_assets | 固定资产、文件检查、权限和有效期 | 不因下一次执行或重启删掉待交付资产 |
| SnowLuma 可见只读目录 | 平台读取已批准文件 | 不挂载整个项目、根配置、数据库或任意工作区 |

`resolved_file` 必须是 SnowLuma 进程实际能读取的路径，例如既有 `/lenbot-files/<asset_id>`，而不是 LenBot 的 `/Users/...`、容器另一命名空间的路径或模型自拟路径。

核对目录 0750、文件 0440 与真实运行 UID/GID 的关系；使用必要的组/ACL或同等最小读权限，不用 0777 解决。只读挂载仍需要目录遍历和文件读取权限。

需要修改现有 SnowLuma 容器挂载时，将重建/重启影响单独列出并取得授权；保留客户端登录状态卷。Gateway Docker CLI 的既有修复不重做，但必须有一条修复后的新 execution 成功结果再继续验收文件生成。

**完成条件：**文件在三个身份下对应同一成品，实际 QQ 客户端能打开中文文件名 CSV，内容和源产物一致；不是只看到上传动作返回一个本地路径。

## F4. 已生成、待交付和已上传三种结果不能混淆

复用现有任务、资产、发送尝试与事件，不新建第二条文件发送队列。至少保证：

- 生成成功、未获上传条件：工作保留具体产物，未完成项说明文件尚未交付；不声称全部完成。
- 准备文件成功：`uploaded=false`，仅说明资产存在。
- 进入实际上传前：再次核对当前群、原主体、原工作修订、文件有效期、既有 SEND_FILE 授予与额度。
- 外发前：持久写入原 action 的尝试事实；重启不会把它误判为从未尝试。
- FILE_UPLOADED：保存真实 file_id、所选实现/协议、原资产和目标群关联，之后才允许“文件已发送”的确认。
- 明确拒绝/连接前失败：保留资产与原因，当前工作不重新生成相同内容来逃避处理。
- unknown：保留占用和原身份；缺少成功事件不等于未发出，不能重传。
- 睡眠延期：保留文件和原事项，实际发送时再查资格；前序未知的依赖消息不继续，其他无关卡片不被阻塞。

首次文件生成与后续上传问题分开计量，不因上传失败再买一次研究和 Python。暂存文件的清理不能早于延期、已尝试未知或仍合法可交付的保留责任。

## F5. 用“本周日程 CSV”做复合能力验收，而不是新增业务特例

### 正常验收请求

在获得真实群操作授权后，由人类提出类似“整理本周直播日程，生成 CSV 并把文件发到本群”的请求。系统应：

1. 依据配置的业务时区和 week_start 确定明确起止范围；返回来源是日程安排，不声称实际直播已经发生。
2. 使用已开放的日程工具取得资料。来源失败、部分范围、没有日程分别表达，不能都写空表成功。
3. 将来源 R 和原问题带入同一信息工作；已有资料不重复抓取。
4. 真正运行 Python 生成文件。推荐列为日期、开始时间、时区、成员、标题、来源链接；不存在的结束时间留空，不编造。
5. 使用 csv 模块或现有库正确处理逗号、引号和换行。中文桌面使用可采用 UTF-8 BOM；这是一项输出选择，不追加 Excel/Office 能力。
6. 读取产物确认表头、记录数量、时间范围和来源完整性，登记并交付实际文件。
7. 最终以 FILE_UPLOADED/file_id 和客户端实际取得文件作为上传证据。

再用一个不依赖日程的“给定表格计算后生成 CSV”请求验证同一通用链，避免特定示例被写死。这里不要求每次都调用浏览器、联网 Python、媒体或额外 Planner。

# 4. P1：旁听准入提高两档，明确改什么、不会改什么

## A1. “提高两档”的本轮定义

源码没有一个已确认的统一两档尺度，也没有提供现场当前 W/p 数值。本轮将它定义为**对所选群当前有效参数的一次显式调整**，不是写一个看似积极的新默认值覆盖生产。

令 p 是抽样概率，W 是窗口秒数，K 是关键词冷却秒数。本轮 +2 的目标：

| 参数 | +2 后的目标 | 说明 |
|---|---|---|
| `attention_sample_probability` | `min(1.0, p + 0.20)` | 增加 20 个百分点；不是乘 1.2 |
| `attention_sample_window_seconds` | `min(W, max(30, W / 2))` | 窗口减半，低于 30 秒的原值不反向调大 |
| `attention_keyword_cooldown_seconds` | `min(K, max(20, K / 2))` | 冷却减半，原来更短或为 0 时保持，不偷偷降低积极程度 |
| `attention_focus_seconds` | 不变 | 不把更多旁听变成更长黏人关注 |
| 模型/工具次数、并发、token/日额度 | 不变 | 观察机会增多不等于赠送无限预算 |
| 睡眠、直接 @、当前授权、连续 Bot 消息限制 | 不变 | 不用放开外部动作来换回复数量 |

这是本轮产品参数建议，可直接实施为“旁听提高两档”的预览操作。+2 应从打开草稿时的有效基线计算，保存具体数值；不要持久化一个每次启动又会乘一次的增益。

如果 p 原来为 0，预览必须明确提示本次将开启随机旁听，而非声称只是无行为变化的小调参。若已到概率上限或窗口下限，展示实际能改变的部分，不伪称一定又上升了完整两档。

**示例，不是用户真实配置：**p=0.10、W=120 秒、K=180 秒 → p=0.30、W=60 秒、K=90 秒。在每个窗口都有合格普通消息、且没有其他抑制条件的假设下，抽样机会从约 3 次/小时变成约 18 次/小时，约六倍。模型实际调用数会受合并、在途对话、睡眠、预算及其他来源影响；回复数还取决于 Agent 是否决定发言。

因此，页面要同时显示“更容易观察”与名义机会密度 `p/W` 的变化，不能只展示一个不带成本含义的积极滑块。数值确定后不悄悄自动调回去；根据正常联调记录再由人类明确调整。

## A2. 支持本群覆盖，但只有一个有效值解析器

**模块：**`config_store.py::SceneSettings`、`runtime/attention.py`、`runtime/scene_policy.py` 或相邻现有策略模块、`agent_runtime.py`、群配置投影。

拟新增少量可选群覆盖，例如：

```text
scenes[group].attention:
  sample_probability
  sample_window_seconds
  keyword_cooldown_seconds
```

缺省继承全局；0、缺省、明确继承的语义分别校验。不要把完整 RuntimeConfig 复制到每个群。读取入口统一为一个小型 `effective_attention(scene_id)`，API 预览、AttentionPolicy、热应用及诊断都调用它，不能各自算一套。

修改只影响选定群的新观察机会；默认不改其他群、不改变历史事件、已准入调用的预算、既有工作主体或已排队发送。全局参数改变的影响范围另行明确显示。

## A3. 窗口长度改变时，不能比较不相容的窗口编号

当前状态保存 `int(now // W)`，并以新编号大于旧编号判断是否抽样。当 W 改变时，新旧编号不再是同一坐标；特别是窗口调大，可能导致长时间不再抽样。[S05]

这次加入群级调参时必须收口这一点。建议将原 SceneSession 中的下一次可抽样时刻保存为绝对时间，或在原状态上明确处理策略变更，二选一实现最短路径。每个窗口仍最多一次；切换配置不回放旧消息、不允许通过连续点击保存反复掷骰。

需要新增一个持久时间字段时，说明这是为替换不能跨配置比较的窗口坐标，不另建抽样任务表。旧状态做一次明确初始化/转换，保留消息和来源身份。

## A4. 参与与消息密度分开

直接 @、回复 Bot、明确称呼、在途跟问和等待回应继续走已实现的快入口；旁听是普通机会，不占用取消、纠正和明确请求的调度优先级。

旁听轮次可以读当前窗口的必要相邻原话来理解群聊动向，但不把整天历史塞进来；已经存在的 recall_chat 保留为需要时回读工具，不重写它。没有明确委托的弱机会不自动建立工作、提醒、账号操作或长期人物认识。

同一群已经有活动对话时，复用现有合并/邮箱；不因 +2 为每条消息另开模型。不引入第二个小模型逐条分类。

**验收：**比较自然聊天时的入库消息数、旁听命中数、实际模型轮次、沉默/表达比例、直接请求等待和模型费用。观察机会明显提高但误接、连续刷屏和直接请求延迟不能被掩盖。

# 5. P1：轻度提高表情选择，不使用随机插图或硬性发图配额

## E1. 先提高模型实际拿到的候选质量

**模块：**`media/service.py::prepare_palette`、`media/store.py`、`cognition/context.py`、既有 `search_media`、素材管理页。

- 将已有 tags 传入模型可见目录；保留 asset 引用、语义说明和真实近期使用。
- 将服务层 40 字符截断改为足以呈现用途的有界描述，例如 120 字符，并标注仍有剩余说明时的可读位置。不要再让下游“允许 80 字”掩盖上游已截到 40 字。
- 候选优先考虑本群允许、运营已标注的表情；相关性、用途多样性和近期重复共同决定少量呈现顺序。
- 候选池不能只循环最近发过的素材。允许尚未使用但标签匹配的运营素材进入，仍按现有目录/查询取得；不自动收集群友私人图片填池。
- 尊重现有 palette 和上下文上限。先在该范围内提高候选质量，不通过翻倍图片数量或默认加载所有像素增加成本。

名称/标签应当足以表达常见情绪和使用场景，但标签来自已有人工素材信息；不在本轮擅自运行视觉模型为整个图库重新标注。

## E2. 增加一个窄的按群表达偏好

建议 `SceneSettings` 增加可选 `expression.sticker_preference`，取 `inherit / natural / slightly_more` 等明确枚举；实际序列化中继承可以通过缺省表示，不同时保存互相矛盾的两种值。

本轮对选定群使用 `slightly_more`：庆祝、赞同、轻松吐槽、接梗和轻度安慰等语境，已有合适授权素材时，更倾向选择一张表情或短文字加表情，而不是默认长文字。

这是一条表达取向，不是“30% 概率强发图”。模型仍决定具体语境是否适合；不新增表情专用审查模型、打分平台或二次决策调用。

以下不因为偏好上调而改变：

- 用户要求只发指定文字，严格照发。
- 严肃求助、技术错误、准确数值和文件完成确认，以清楚表达为先。
- 确定性日历卡、群报告图、文件行动不被额外塞表情。
- 运营已授权的表情可按描述选取；分析图片内容时仍必须实际取得像素。
- 没有合适素材时正常文字，不为了“达到频率”使用不相关或重复图片。

不要自动修改人格正文或人工样例；偏好以单独的当前群配置投影进入现有表达提示。

## E3. 判断“略微增加”的口径

按可使用表情的日常轻松回复统计，而不是所有输出。把直播卡片、技术截图、工作图表和文件剔除后，再看运营表情所占比例。

首轮将“同类轻松语境下相对略有提升、重复素材不过度集中”作为观察目标。可以把相对基线增加约 20%—30% 作为调参参考，例如原来 10% 变为约 12%—13%，不是要求所有群达到固定比例，也不能承诺模型一定输出该频率。

记录候选有无、是否装入最终窗口、模型选取、最终真实发送四层。候选没呈现与模型没选不是同一个问题，不能只堆提示词。

# 6. P1：新群进入一个界面就能配置，而不是更多跳转入口

## G1. 页面入口与新群发现

保留上一轮六入口导航；这次不再重排导航。交付一个真正的“群聊快速配置”页/工作台，在群列表的每个群上直接进入，新增群默认也走它。

“已加入”与“已配置”分开。现有 `/api/setup/options` 只列 root.scenes，已有向导对未在根配置中的群返回阻断；这无法独立覆盖加入新群的场景。[S07]

以当前 OneBot 的受信只读群列表/真实入群通知补充发现，合并已经保存的群和已观察但未配置的群，显示实际群号与名称。不能假装有通知就已获自动发言授权；刚发现的群在显式保存前不启动聊天、播报、研究或工具执行。

群列表读取失败时保留已知列表并说明样本时间，不伪称空列表就是没有群。可以提供人工输入真实群号的配置入口，但对“是否已加入”的状态保持明确，不创建虚假群成员事实。

## G2. 一页布局

```text

本群参与
  启用本群 | 普通成员聊天 | 白名单例外说明
  旁听 +2 档 | 当前概率/窗口/关键词冷却 | 恢复继承
  表情：自然 / 稍多 | 睡眠继承与临时叫醒状态

  网页、公开 B站、日程、群报告

  直播/动态播报、兴趣分享
  [每行：本群开关、实际状态、缺什么、展开参数]
```

桌面可双列，窄屏单列；重要操作和错误仍在当前页面。默认折叠高级参数，不一次渲染全部原始 Schema。

全局端点或凭据缺失时，在当前页面内联抽屉打开所属共享表单；全局修改必须注明会影响哪些群，并保留本群草稿。确需平台部署操作时明确标为现场步骤，不能承诺一个网页开关会自动构建浏览器、创建容器或获得账号权限。

## G3. 开关的业务语义

| 开关/参数 | 实际应修改 | 不应顺便修改 |
|---|---|---|
| 本群普通聊天 | 现有 enabled/chat | 不自动开放外发和账号动作 |
| 本群资料/Python等工具 | 现有 scenes[group].plugins 及必要已配置参数 | 不自动更换后端、模型或公开出口 |
| 本群文件发送 | 既有文件交付资格与选定成员 SEND_FILE 授予 | 不因群总开关授予所有成员、系统心跳和其他群 |
| 本群兴趣分享 | 既有插件场景参数、插件主体 Grant、次数/冷却 | 不自动创建系统研究、不改变其他群发布 |
| 本群旁听 +2 | 新的少量本群 attention 覆盖 | 不增加模型次数预算、关注时长或权限 |
| 表情稍多 | 本群 expression 偏好 | 不改人工人格、图库归属或原样发送要求 |
| 语义检索 | 现有 semantic_retrieval 明示同意 | 不扩大跨群读取或隐式发送原话给新供应商 |

文件申请者复用现有人类 Grant。首版用真实成员多选，不创建未实现的 `principal_id='*'`，不把“本群打开文件能力”误译为所有人都已获授权。普通能力保持原有聊天/工作规则，不反过来要求每个普通读取都新增手工 Grant。

对全局文件大小和群日上传上限等现有参数，先展示有效值和来源。若本轮需要按群限制，只允许在当前全局硬上限之内增加少量明确覆盖并统一解析；没有这个需求就不制造新的资源策略层。修改共享参数要在当前页明确其全局影响。

## G4. 保存必须是一个明确的配置事务

**复用：**现有 `ConfigEdit`、`merge_edit`、`config_update_lock`、`credential_revision`、RootConfig 校验和保存，不新增 quick_group_config 数据库。

可以沿 `/api/setup` 增加一个严格类型的 group_quick 配置请求，或者扩充既有群配置端点；选定一条主写入路径，不同时维护新旧两套业务规则。

请求包括本群草稿的基线、实际修改字段、涉及 Grant 的基线/修订及必要的共享配置变更。秘密仅传 keep/replace/clear 与世代，不返回原值。

执行步骤：

1. 在原锁内读取最新根配置。
2. 对明确修改的字段进行基线比较；未修改字段保留最新值。
3. 把本群参数、插件记录和用户明确确认的授权变更装配为一个候选。
4. 全量校验候选，包括依赖是否存在、主体/权限是否有效；无效配置不写入磁盘。
5. 一次保存，之后按原模块热应用；读回分别显示 saved/effective/apply_error/requires_restart。
6. 应用失败不冒充保存失败，也不自动换后端；用户草稿与确认意图可回看。

**预览必须约束应用。**当前 WizardRequest 只有 wizard/values，apply 可以重新依据当前配置计算预览。新的一页操作不能在用户确认后悄悄应用一份不同的计划；保存需核对用户预览的原值/相关世代，冲突时让用户比较基线、当前值、自己的改动。[S07]

把这个规则也用于现有研究向导：授予查找需复用当前授权判定，包含到期等真实条件；不只用 enabled/类型/主体判断“已有授予所以可用”。不在本轮复制第二份授权判断。

## G5. 从旧群和旧参数平滑进入同一页面

这里的“平滑”指保留已存在事实和配置，而非长期两套运行语义。

- 旧群没有新 attention/expression 字段时继承全局，不自动获得积极旁听或额外发图。
- 用户在预览中选定哪些群应用 +2 / 表情稍多；不能改全部历史群。
- 新群可以选择本轮偏好的草稿预设，但首次保存前保持不生效。
- 空场景参数插件继续接受 `{}`；有必填参数的插件在本行显示错误，不能要求填虚假字段。
- 旧插件高级页保留，但与本页共享字段组件、保存合同和冲突处理，不维护副本。
- 已加入群同步、预览和浏览配置不发模型请求、不发群消息；点击保存也不自动上传文件作为“自检”。

**完成条件：**运营者在一个群页面完成“开启日程与 Python、为选定成员开放文件、旁听 +2、表情稍多、设直播订阅、明确不启用账号动作”，保存一次后能看懂哪些已生效、哪些缺全局条件。

# 9. 接手首轮必须做什么

1. 固定当前 HEAD；若已经前进，重新定位本计划列出的符号，已经修好的不重复改。
2. 先修 `respond` 文件三处合同和文件候选投影；同时核对所选 SnowLuma 版本与专用资产只读目录。
3. 在获准环境取得一条新 Python 成功和完整文件交付，不能只更新 deployment 标记。
4. 增加少量本群 attention/expression 覆盖及统一解析；按预览给选定群 +2 和表情稍多。
5. 将新群创建、常用能力开关和实际参数收进同一页；复用现有配置基线、凭据世代与运行应用机制。
6. 精简 iteration 到本轮真实结论、未验项和下一步。旧失败保留在 Git/事件历史，不反复复制过时“未启动”段落到已有运行记录后面。

交付格式：基线与变更提交、已修实际断点、修改文件与完整链路、实际执行的构建/人工操作、真实结果身份、未验分支、现场配置变更范围。不得以补了一张新页面或修改一条说明就宣布复合 Agent 全部跑通。

## 发布判定

- 文件样例通过，才能声明“已验证资料整理→Python→CSV→目标群文件”的这个能力子集。
- 旁听和表情变更需要独立说明所选群、旧值、新值与观察范围，不用全局消息数掩盖误接。
- 群配置必须允许新人不理解插件 ID/Grant ID 就完成常用操作；高级开发入口仍保留。
- 其他尚未满足的浏览器、公开出口、媒体/转写、账号或 Core 条件，继续按实际状态显示，不由本轮自动放行。
