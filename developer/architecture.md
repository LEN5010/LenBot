# 架构

这份文档写给想改 LenBot 本身的人，说明各部分做什么、数据怎么流动。字段和默认值以源码为准，源码目录对照见 [CONTRIBUTING](../CONTRIBUTING.md#源码结构)。

## 整体

LenBot 是一个单进程宿主，按群聊场景组织：

- 每个场景（一个群或一个私聊）有一份持久的 Agent 会话。
- 消息、插件事件、任务进展和定时提醒都作为这个会话的输入。
- 主脑模型读完整上下文，自己决定说什么、调用哪些工具。
- 宿主不替模型判断语境，只负责三件事：真实身份、会话连续性、执行状态。

```text
OneBot ──> 平台适配器 ──> 消息入库 ──┬─> 插件规则直接处理（不经过模型）
                                    └─> 注意力决定开轮 ──> 主脑工具循环 ──> 表达／工具／任务
                                                              ^
                       插件事件、任务事件、提醒 ───────────────┘
```

长工作交给独立容器，长期记忆由本地记忆服务维护，插件和宿主在同一进程。普通聊天不依赖任务容器或外部服务。

`len-bot` 命令进入 `launcher.py`，启动器只管一个 `len_bot.next.host` 子进程。宿主退出码为 75 时，启动器再启动一次，面板的重启就是这样实现的；其他退出都结束启动器。

## 平台

`platform/` 把平台原生事件转成统一消息和通知。目前只有 OneBot 适配器，QQ 消息段和接口只在 `platform/onebot*.py` 里出现。

- 账号写成 `平台:账号`，例如 `onebot:70001`。
- 场景写成 `平台:group:群号` 或 `平台:private:账号`。
- 提及统一为 `mention`，语音统一为 `audio`。
- 原始事件单独保存；通知的规范字段存在 `notices.body`，业务代码不再解析 OneBot 原始字段。

## 聊天

| 模块 | 职责 |
|---|---|
| `runtime/network.py` | 连接平台，把消息分给场景 |
| `chat/attention.py` | 决定什么时候开一轮 |
| `chat/session.py` | 主脑工具循环 |
| `chat/context.py` | 组装模型请求 |
| `chat/expression.py` | 台词、表情、引用和发送 |

**会话**：`messages` 保存真实收发，`mind_entries` 保存已经交给模型的批次和完整的工具交换。轮次只是执行单位，结束一轮不会清空会话。

**请求顺序**：稳定的角色和能力说明、旧回想、原话和工具交换、本轮宿主参考。原话保留真实账号、时间、消息 ID、引用和媒体状态。

**表达**：同一个主脑决定态度、对象、台词和工具。`say.content` 就是要发的正文，`react` 可以单独发表情；模型的普通文字不会发出去。素材选中、模拟发送、平台确认和失败分别记录。

**收轮**：生成期间新到的消息照常入库，不会插进已经发出的请求。一组工具执行完、最后一次表达带 `end_turn=true` 时这一轮结束，后来的消息留给下一轮；否则把新消息和事件追加进去，再请求一次。

**压缩**：输入估算超过 `compaction.input_tokens` 时，把较早的完整消息和工具组整理成回想，原数据不删除。估算优先用上次请求的实际用量，否则按字节估算。细节见[上下文与模型输入](context.md)。

**续接协议**：调用记录保存完整的原始响应。`history_policy=native` 原样回传历史；`omit-reasoning` 省去可读的思考内容并带稳定的 `Session-Id`，只用于自己维护续接的中转服务。

## 角色与学习

角色包由 `persona/` 读取，说明见[角色包](personas.md)。提示词在 `src/len_bot/prompts/`，原则说明见[群聊表达](expression-materials.md)。

`learning/` 从群聊里学习，每个群分别开关，各自绑定模型：

| 能力 | 做什么 |
|---|---|
| 表达 | 提取群友有特点的说法，每轮按近期对话选几条作参考 |
| 黑话 | 找出群里的特殊用词并推断含义，可以人工固定或禁用 |
| 表情 | 收集群里的图片并标注，采用后可以和角色表情一起用 |
| 回复效果 | 观察 Bot 说完话后群友的反应，供复盘，不自动改角色 |

学到的内容只作为参考进入上下文，不冒充角色设定或群聊经历。

## 记忆

`memory/` 是唯一的长期记忆后端，正文是本地 Markdown：

- `public/` 放明确公开的资料；
- `scenes/<场景>/` 放各场景自己的记忆，下面再分 `people/<账号>/`、`events/`、`bot/<角色ID>/`、`resources/`。

群聊只读当前场景和公开资料，同一个人在不同群的记忆不合并。`.memory-index.sqlite3` 保存索引、修改历史和目录摘要生成时间，不是缓存，不能随便删。摘要生成与正文变更都使用应用时钟，过期判断不读取文件 mtime。

每轮开始时自动召回：先读最近几位发言人的画像，再用最近对话检索。召回结果只放进本轮参考，不写进会话历史。后台整理按批读取新消息，由 memory 模型浏览、搜索、改写记忆文件，整批成功才推进进度。

## 工具

`chat/tools.py` 管工具目录和分派。一个工具同时满足下面几条才会出现：

- 有实现；
- 根配置开启；
- 场景允许；
- 角色的 `tools` 许可包含它。

常用工具直接给模型，低频工具要先通过 `tool_search` 发现，下一次请求才带上它的参数定义。工具出错时原样返回给模型，宿主不重试、不换服务。网页、文件和插件返回的内容只是资料，不当作执行授权。

MCP 服务的工具和插件工具走同一套发现和许可。技能是 `SKILL.md` 加资源文件，只读挂进任务容器。

## 后台任务

`work/` 用 Pi 在独立 Docker 容器里完成长工作，聊天不等它结束。

- `delegate` 用真实请求人和场景建任务，`task` 用来查询、回答、追加、取消和续接。
- 完成事件回到原场景的会话。
- 容器以非 root 运行，根文件系统只读，没有网络；模型和公网请求经宿主转发，真实密钥留在宿主，任务只拿到本任务的令牌。
- 输入文件是只读快照，产物登记为交付后才能下载或发送。

浏览器有两种：任务容器里的匿名 Chromium，以及主人配对的账号浏览器。

## 插件

插件是宿主同进程的可信 Python 代码，用来处理精确命令、平台事件、后台监测和专用工具。接口见[插件 v1](plugins-v1.md)。

- **匹配**：命令、全文、正则依次匹配纯文本，每条消息最多被一个插件接管。插件处理的消息和结果会进入会话作为背景，但不会因此唤醒模型。
- **唤醒**：`send` 直接发送；`emit_event` 会唤醒主脑。
- **安装**：Git 和 ZIP 都先准备候选，再明确应用。依赖没变的插件定向重载；依赖变化或声明需要重启的，在下次重启的停机阶段统一安装。
- **目录**：插件都在实例根的 `plugins/` 下。已安装源码在 `plugins/<名字>/`，候选在 `plugins/.candidates/`，来源记录在 `plugins/.installations/<名字>.json`，插件数据默认在 `plugins/.data/<名字>/`，卸载时保留。手工复制进 `plugins/` 的插件也会被发现。

## 配置与权限

`lenbot.config.json` 是唯一的运行参数来源，入口一次解析、完整校验。面板和群里的管理工具都通过 `configuration/editing.py` 保存，共用一把写锁。插件配置定向重载，其他修改等明确重启后生效。

权限只看真实身份，判断谁在请求、指的是谁交给模型：

- `owners` 是全局主人；
- 场景管理员、白名单、黑名单和群角色参与各项能力的判断；
- 群里的管理工具只对主人和全局管理员开放。

宿主、面板和维护命令都要先拿到实例锁 `.lenbot-instance.lock`，防止同一个实例被启动两次。

## 存储

一个 SQLite 业务库保存消息、会话、轮次、模型调用、任务、提醒、学习和插件事件，各领域的表和查询由所属模块维护。`storage/schema.py` 一次建好全部表。另有记忆处理库 `<数据库>.memory.sqlite3`，保存记忆整理的进度。

业务库的公开格式从 v1 开始。改结构时：

1. 在 `schema.py` 直接写新结构；
2. 在 `maintenance/migrate.py` 加一步升级；
3. 提高 `FORMAT_VERSION`。

升级只由停机后的维护命令执行，运行时不兼容旧格式。

运行记录都在业务表里（消息、轮次、模型调用、任务事件、学习调用），没有另外一套审计。宿主日志按天轮转。`retention` 为空时不自动清理。

## 面板

后端在 `panel/`，按业务分路由；前端是 `web/frontend/` 下的 Vue 3 + Vuetify。业务请求集中在 `src/host/api/`，通用组件在 `src/host/ui/`，颜色和尺度在 `src/styles/`。面板文案写给运营者看，说清对象和后果，不写开发细节。

视觉规范：

- 颜色只在 `styles/theme.js` 定义。品牌粉 `brand`（#E799B0）只用于标志、导航选中竖条、图表和开关的开启态；按钮和链接用加深的 `primary`，其余用中性灰。不用渐变、毛玻璃和回弹动画。
- 圆角三档：控件 6px、小块 8px、卡片 12px。
- 按钮分四级：主要按钮 `color="primary"`，每个区域最多一个；次要按钮 `variant="outlined"`（旧页面的 `tonal` 也按次要按钮显示）；文字按钮 `variant="text"`；危险按钮 `color="error"`，只用于确认删除这类破坏性操作。
- 输入框统一 outlined、comfortable，由 `plugins/vuetify.js` 的默认值设置，页面里不单独改。
- 选中态统一用浅色底加粉色竖条，文字保持正文色；分段选择（`v-btn-toggle`）和页面标签一样是灰色底槽加白色选中块。标签、状态小块用中性色，不用 primary。
- 插件参数表单由 `host/components/SchemaForm.vue` 按清单生成，不为单个插件写专用表单。
- 首页的待处理事项在 `host/attention.js` 里汇总，顶栏的提醒数字和首页列表共用这一份。

## 发行

`scripts/build_release.py` 从同一次提交构建 wheel、源码包和 Linux／macOS 部署包，Docker 宿主镜像安装同一个 wheel。部署包里 `releases/<版本>` 放程序和依赖环境，`instance/` 放数据，升级时先装新版本、停机迁移、恢复插件依赖，再切换 `current`。
